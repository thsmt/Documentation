Application Load BalancerでTLS終端

EC2上のApacheに第三者認証局の証明書を配置してHTTPSを終端する構成から、Application Load BalancerとAWS Certificate ManagerでTLSを終端する構成へ移行します。EC2作成、移行前構成の再現、ALBの事前試験、Route 53切替、切り戻し、移行後の証明書運用までを対象とする

⚠️ DNSレコードは最後に変更

先にACM証明書、ターゲットグループ、ALB、Apache設定、ヘルスチェックを完成させ、ALBのDNS名を使った事前試験に成功してからRoute 53を変更します。DNSを先にALBへ向けると、未完成の経路へ利用者通信が流れる

ℹ️ ACMの自動更新とEC2への配置は別の処理

DNS検証用CNAMEを残し、証明書をALBで使用している場合、ACMは証明書を自動更新してALBへ反映します。一方、エクスポートしたACM証明書や第三者証明書をEC2内へ配置した場合、ACMの更新だけではサーバー上のファイルは更新されません。サーバー内でTLSを終端する場合は、ACMEまたはAWS Workload Credentials Providerなどの再配置手段が必要

⚠️ 公開TLS証明書の有効期間短縮

ACMパブリック証明書は2026年2月18日以降198日になり、ACMは期限45日前から更新します。業界要件では最大有効期間が2027年3月15日から100日、2029年3月15日から47日へ段階的に短縮されるため、第三者証明書を人手で発行・配置する運用は作業頻度と失効リスクが増える。詳しい日程はACM / TLS証明書 - 有効期間と今後の短縮を参照する

0. 目的と完成構成

0.1 移行前と移行後

項目移行前移行後
公開URLhttps://alb-lab.zexample.comhttps://alb-lab.zexample.com
TLS終端EC2上のApacheApplication Load Balancer

完成後の通信経路は、クライアントからALBまでがHTTPS、ALBからEC2までがHTTPです。EC2のSecurity GroupはALBのSecurity GroupからのTCP/80だけを許可し、インターネットからEC2へWeb通信を直接到達させない

⚠️ ALBを配置してもEC2 1台の可用性は上がらない

ALBは複数AZのサブネットへ配置しますが、ターゲットがEC2 1台だけの場合、そのEC2は単一障害点のままです。高可用性が必要な場合は、異なるAZに複数EC2を配置し、Auto Scalingまたは同等の復旧方式を追加する

0.2 ALB終端を選ぶ理由

観点ALBとACMEC2内で証明書を管理
公開証明書料金ACM統合サービスで使う非エクスポート型パブリック証明書は追加料金なし第三者証明書またはエクスポート可能な証明書の料金が発生
更新作業DNS検証CNAMEと利用状態を維持すればACMが自動更新再発行、再配置、構文確認、再読み込みが必要
インフラ料金ALB稼働時間、LCU、データ転送などの料金が発生ALB料金はないが、EC2の公開IPv4や運用作業の費用を考慮
秘密鍵ALB用の秘密鍵をEC2へ置かないEC2上で秘密鍵の保護が必要
拡張性複数ターゲット、パスルーティング、WAF連携へ拡張可能サーバーごとの構成管理が必要

ALBには固定時間料金とLCU料金が発生するため、証明書費用だけでなくALBの月額、運用工数、可用性、WAF連携の必要性を含めて比較する。料金単価はリージョンと利用量で変わるため、導入時点のElastic Load Balancing料金を確認する

4.1 第三者証明書の配置

実環境と同じ状態を再現する場合は、発行済みのサーバー証明書、秘密鍵、中間証明書チェーンを安全な経路でEC2へ配置します。検証だけの場合は自己署名証明書でもApacheの構成確認はできますが、ブラウザーでは信頼エラーになる

4.2 移行前VirtualHostの作成

HTTPをHTTPSへ転送し、EC2の443で第三者証明書を使用する移行前設定を作成する

/etc/httpd/conf.d/alb-lab.zexample.com.conf
<VirtualHost *:80>
    ServerName alb-lab.zexample.com
    DocumentRoot /var/www/html

    RewriteEngine On
    RewriteRule ^ https://alb-lab.zexample.com%{REQUEST_URI} [R=301,L]

    ErrorLog /var/log/httpd/alb-lab_error.log
    CustomLog /var/log/httpd/alb-lab_access.log combined
</VirtualHost>

<VirtualHost *:443>
    ServerName alb-lab.zexample.com
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile /etc/httpd/conf/ssl/alb-lab.zexample.com.crt
    SSLCertificateKeyFile /etc/httpd/conf/ssl/alb-lab.zexample.com.key
    SSLCertificateChainFile /etc/httpd/conf/ssl/alb-lab.zexample.com-chain.crt

    ErrorLog /var/log/httpd/alb-lab_ssl_error.log
    CustomLog /var/log/httpd/alb-lab_ssl_access.log combined
</VirtualHost>

認証局からfullchain形式のファイルが提供される場合は、サーバー証明書と中間証明書をSSLCertificateFileで読み込み、SSLCertificateChainFileを省略する構成もあります。採用する形式は認証局の手順とApacheのバージョンに合わせる

構文確認後にApacheを再読み込みする

Apache validation
sudo apachectl configtest
sudo systemctl reload httpd
sudo apachectl -S

curl -I http://alb-lab.zexample.com/

7. ApacheをALB経由に対応

7.1 リダイレクトループを防ぐ設定

ALBでTLSを終端し、ターゲットグループをHTTP:80にすると、Apacheから見える接続自体はHTTPです。Apacheが接続方式だけを見てHTTPSへ転送すると、ALBとApacheの間でリダイレクトが繰り返されます。ALBが付与するX-Forwarded-Proto: httpsを確認し、HTTPSで到達した利用者を再転送しない

切替中もEC2への直接HTTPをHTTPSへ転送できる移行用設定へ変更する

/etc/httpd/conf.d/alb-lab.zexample.com.conf
<VirtualHost *:80>
    ServerName alb-lab.zexample.com
    DocumentRoot /var/www/html

    # ALBのHTTPSリスナーから転送されたことをアプリケーションへ伝える
    SetEnvIf X-Forwarded-Proto "^https$" HTTPS=on

    RewriteEngine On
    # ALBヘルスチェックは200を返す
    RewriteCond %{REQUEST_URI} !^/healthz$
    # 利用者がALBへHTTPSで接続済みの場合は再転送しない
    RewriteCond %{HTTP:X-Forwarded-Proto} !^https$ [NC]
    RewriteRule ^ https://alb-lab.zexample.com%{REQUEST_URI} [R=301,L]

    ErrorLog /var/log/httpd/alb-lab_error.log
    CustomLog /var/log/httpd/alb-lab_access.log combined
</VirtualHost>

# 切り戻し期間中は既存の443 VirtualHostを残す
<VirtualHost *:443>
    ServerName alb-lab.zexample.com
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile /etc/httpd/conf/ssl/alb-lab.zexample.com.crt
    SSLCertificateKeyFile /etc/httpd/conf/ssl/alb-lab.zexample.com.key
    SSLCertificateChainFile /etc/httpd/conf/ssl/alb-lab.zexample.com-chain.crt

    ErrorLog /var/log/httpd/alb-lab_ssl_error.log
    CustomLog /var/log/httpd/alb-lab_ssl_access.log combined
</VirtualHost>

設定変更前後のファイルを保存し、構文、ローカルヘルスチェック、直接HTTPの転送を確認する

Apache checks
sudo cp -a \
  /etc/httpd/conf.d/alb-lab.zexample.com.conf \
  /etc/httpd/conf.d/alb-lab.zexample.com.conf.$(date +%Y%m%d%H%M%S).bak

sudo apachectl configtest
sudo systemctl reload httpd

curl -i http://127.0.0.1/healthz
curl -I -H 'Host: alb-lab.zexample.com' http://127.0.0.1/
curl -I \
  -H 'Host: alb-lab.zexample.com' \
  -H 'X-Forwarded-Proto: https' \
  http://127.0.0.1/
試験期待結果
/healthz200 OK
直接HTTP、X-Forwarded-Protoなし301で公開HTTPSへ転送
X-Forwarded-Proto: httpsあり200 OK、再転送なし
⚠️ 転送ヘッダーを無条件に信頼しない

X-Forwarded-ForやX-Forwarded-Protoは利用者も送信できます。移行後はEC2のTCP/80をALB用Security Groupからだけ許可し、アプリケーション側でも信頼するプロキシをALB経路へ限定する

10. DNS切替前のALB事前試験

ALBのDNS名を確認します。公開FQDNのDNSレコードはまだEC2を向いているため、curl --connect-toを使って接続先だけをALBへ変更します。URL、Hostヘッダー、TLSのSNIはalb-lab.zexample.comのまま維持できる

pre-cutover test
ALB_DNS_NAME='<ALB_DNS_NAME>'

curl -I \
  --connect-to "alb-lab.zexample.com:443:${ALB_DNS_NAME}:443" \

openssl s_client \
  -connect "${ALB_DNS_NAME}:443" \
  -servername alb-lab.zexample.com \
  -showcerts < /dev/null 2>/dev/null |
  openssl x509 -noout -subject -issuer -serial -dates

HTTP:80のリダイレクトはALBのDNS名へHostヘッダーを付けて確認する

HTTP redirect test
curl -I \
  -H 'Host: alb-lab.zexample.com' \

13. 観察期間後の旧TLS設定終了

DNSキャッシュ、長時間接続、外部監視、バッチ、固定IP参照の影響を確認するため、組織で定めた観察期間は旧EC2の443設定と証明書を切り戻し用に保持します。確認後、次の順で直接公開を終了する

  1. EC2のアクセスログに旧経路の新規通信がないことの確認
  2. 外部監視、バッチ、連携先が公開FQDNを使用していることの確認
  3. EC2用Security Groupからインターネット送信元の80／443を削除
  4. ALB用Security GroupからEC2の80へ到達できることの再確認
  5. Apacheの443 VirtualHostを無効化する変更の実施
  6. apachectl configtest成功後のApache再読み込み
  7. 旧証明書と秘密鍵の保管または削除を組織の鍵管理規程に沿って実施
  8. EC2のパブリックIPv4が不要な場合の削除検討

最終的なApache設定は80番VirtualHostだけにできます。HTTPからHTTPSへのリダイレクトはALBで完結するため、EC2側のRewrite設定を削除する場合は、ALB以外の経路が存在しないことを先に確認する

⚠️ インスタンスをプライベートサブネットへ移動する変更は別作業

既存EC2のサブネットは後から変更できません。プライベートサブネット化する場合は、AMIまたはIaCから新しいEC2を作成し、ターゲット追加、Healthy確認、旧ターゲットのdrainingを経て入れ替える

14. 切り戻し

14.1 DNS切替前

ALB事前試験に失敗した場合はRoute 53を変更せず、既存のEC2直接TLS終端を継続します。Apache設定をバックアップから戻し、ALBとターゲットグループの原因を調査する

14.2 DNS切替後

  1. 旧EC2の443 VirtualHostと第三者証明書が有効であることの確認
  2. EC2用Security Groupの直接443許可が有効であることの確認
  3. Route 53のalb-lab.zexample.comを変更前のAレコードへ復元
  4. DNS応答が旧EC2のIPへ戻ることの確認
  5. HTTPS応答と旧証明書の確認
  6. ALB経路の5XX、ターゲットヘルス、Apacheログ、アプリケーションログの保全
⚠️ 切り戻し完了まで旧証明書を削除しない

DNSキャッシュによりALB経路とEC2直接経路が一時的に混在します。両方の経路が正常である期間を確保し、切替完了を確認する前に旧証明書、443 VirtualHost、Security Groupルールを削除しない

17. サーバー内でTLS終端する場合

規制、アプリケーション要件、ALBからEC2間の暗号化要件により、EC2内でTLSを終端する構成を残す場合があります。実機での手動エクスポートとAWS Workload Credentials Providerの導入は、ACM証明書をEC2へ自動配置を参照する。証明書方式、有効期間、料金、ACME、EventBridgeとSystems Managerによる配布方式の比較は、AWS Certificate Manager (ACM) と証明書運用を参照する

ℹ️ サーバー内の自動更新方式

AWSは、公開証明書を利用者管理のサーバーへ自動配置する第一候補としてACMEを案内しています。ACMEを利用できない場合は、エクスポート可能なACM証明書をAWS Workload Credentials Providerが定期取得し、ファイル更新後にApacheのreloadコマンドを実行する方式を選択できる
