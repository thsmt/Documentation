Git / GitHub 実践編

チーム開発とIaC運用で必要になる、更新取り込み、コンフリクト解消、rebase、取り消し、Pull Request運用、秘密情報の初動を安全な順序で整理する

基本編から進む前に

基本編のclone、ブランチ、commit、push、Pull Requestを一通り実施できることを前提とする。本ページは、共有ブランチの更新、競合、レビュー、誤操作への対応を扱う。実際の本番リポジトリで初めて試さず、個人の検証用リポジトリまたは作業ブランチで練習する

難易度扱う範囲到達目標
基本編導入、認証、clone、ブランチ、PR、レビュー小さな変更をブランチから安全に提案できる
実践編競合、rebase、取り消し、PR運用、秘密情報の初動共有リポジトリで問題を切り分け、安全な復旧判断ができる
上級編の候補GitHub Actions、rulesets、CODEOWNERS、署名、release、複数リポジトリ運用チームの変更管理ルールを設計・改善できる

1. 作業開始時の更新確認

変更を始める前に、現在のブランチ、未コミット変更、リモートの更新を確認する。未コミット変更を抱えたまま更新取り込みを始めない。差分が残る場合はcommit、stash、破棄のいずれかを意図して選ぶ

powershell
git status --short --branch
powershell
git fetch origin --prune
powershell
git log --oneline --decorate --graph HEAD..origin/main
powershell
git diff --stat HEAD..origin/main

自分の作業ブランチへ最新のmainを取り込む方式は、チームのルールに従う。履歴を書き換えないmergeと、個人ブランチの履歴を直線化するrebaseを混在させる場合は、PR作成前に方式を確認する

2. コンフリクトの解消

同じ行の別変更、削除と編集の競合などで、Gitが自動判断できない状態をコンフリクトと呼ぶ。内容を理解せずに片方を削除しない。変更意図、テスト、設定ファイルの整合性を確認してから解消する

  1. 作業ツリーと現在のブランチを確認
  2. 更新元をfetchし、指定された方式でmergeまたはrebaseを開始
  3. git statusで競合ファイルを確認
  4. 競合マーカーを編集し、残す内容を選択または統合
  5. 対象ファイルをgit addし、mergeまたはrebaseを完了
  6. テスト、差分、PRを確認
powershell
git merge origin/main
powershell
git status
powershell
git diff --name-only --diff-filter=U
powershell
git add <RESOLVED_FILE>
powershell
git commit
⚠️ 競合マーカーを残さない

<<<<<<<、=======、>>>>>>>が残ると、設定ファイルやアプリケーションを壊す可能性がある。commit前に検索し、テストまたは構文検証を実行する

powershell
git grep -n -e '<<<<<<<' -e '=======' -e '>>>>>>>'

3. rebaseを安全に使う

rebaseは、作業ブランチのコミットを新しい基点の上へ並べ直す。自分だけが使うブランチでは履歴を読みやすくできる一方、共有済みブランチのコミットIDを変えるため、他者が利用しているブランチには事前合意なしで実行しない

操作使う場面注意
git rebase origin/main個人ブランチを最新mainへ追従push済みならPRへの影響を確認
git rebase --continue競合を解消して次のコミットへ進む先に競合ファイルをgit add
git rebase --abortrebase開始前の状態へ戻す判断に迷う場合は最初に使用
git push --force-with-lease合意済みの個人ブランチを更新--forceより安全だが、共有ブランチには使用しない
powershell
git fetch origin --prune
powershell
git rebase origin/main
powershell
git rebase --continue
powershell
git rebase --abort

4. 取り消しと復旧の使い分け

取り消し操作は、変更がどこまで共有されたかで選ぶ。共有済みの履歴を変更するresetや強制pushを、問題解決の第一手にしない

状況優先する操作共有ブランチでの扱い
未ステージの変更を取り消すgit restore <FILE>ローカルのみ
ステージングだけを外すgit restore --staged <FILE>ローカルのみ
公開済みcommitを打ち消すgit revert <COMMIT>新しい打消しcommitを追加
個人ブランチの直前commitを作り直すgit resetを検討push済みなら事前合意が必要
失った参照を探すgit reflog復旧候補を確認してから操作
powershell
git revert <COMMIT_SHA>
powershell
git reflog
⚠️ mainでresetしない

mainや共同利用ブランチでのreset --hard、push --forceは他者の履歴と作業を失わせる可能性がある。公開済みの誤変更は原則としてrevertで戻し、例外はリポジトリ管理者と復旧手順を合意してから実施する

5. stashとcherry-pick

stashは未コミット変更を一時退避する操作、cherry-pickは選択したcommitだけを現在のブランチへ適用する操作である。どちらも便利だが、退避内容の放置や二重適用を避けるため、使用後に差分と履歴を確認する

powershell
git stash push -m "wip: <WORK_DESCRIPTION>"
powershell
git stash list
powershell
git stash pop
powershell
git cherry-pick <COMMIT_SHA>
powershell
git cherry-pick --abort

6. Pull Requestとレビューの運用

PRは、何を変え、なぜ変え、どのように確認したかを共有する単位である。変更を小さく分け、PR説明には目的、影響範囲、検証結果、ロールバック方法、確認してほしい観点を記録する

作成者の確認レビュー担当の確認
対象外ファイル、秘密情報、生成物、巨大ファイルが含まれない変更目的と実装が一致し、既存仕様を壊していない
テスト、lint、リンク確認、差分確認の結果を記録失敗時の影響、ロールバック、権限・設定変更の妥当性を確認
base branch、レビュー依頼先、CI結果を確認コメント解決後に再確認し、必要ならApproveまたはRequest changesを選択
powershell
gh pr status
powershell
gh pr create --fill
powershell
gh pr checks

重要ブランチは、PR必須、承認必須、CI成功必須、会話解決必須、force push禁止をrulesetまたはbranch protectionで設定する。レビューのRequest changesを実際にマージ阻止するには、リポジトリ側の保護設定が必要

7. 秘密情報をcommitした場合の初動

アクセスキー、トークン、パスワード、秘密鍵をcommitまたはpushした場合は、履歴削除より先に無効化またはローテーションを行う。ファイルを次のcommitで削除しただけでは、過去の履歴、fork、clone、PR参照から秘密情報が見える可能性がある

  1. 対象の認証情報を無効化またはローテーション
  2. 影響範囲、公開範囲、利用履歴を確認
  3. 新しい秘密情報をコード・設定ファイル・ログへ記録しない
  4. .gitignore、テンプレートファイル、Secrets Managerなどで再発を防止
  5. 履歴削除が必要な場合は、管理者と利用者に影響を共有し、公式手順に従う
⚠️ 秘密情報の履歴書き換え

git-filter-repoによる履歴書き換えと強制pushは、既存clone、fork、PR、署名、共同作業へ影響する。単独で実行せず、認証情報の無効化を先に完了し、公式手順と管理者判断に従う

8. IaC変更の実践チェック

CloudFormation、Terraform、Kubernetes、CI設定などは、テキスト差分が小さくても影響が大きい。PR前に、変更対象、作成・更新・削除の差分、権限、ネットワーク、秘密情報、ロールバックを確認する

powershell
git diff --check
powershell
git diff origin/main...HEAD -- <TARGET_DIRECTORY>
確認対象具体例
変更の種類作成、更新、削除、置換、権限拡大の有無
環境差分account、Region、CIDR、ARN、ドメイン、タグ、変数ファイル
検証format、validate、plan、change set、静的解析、テスト
復旧ロールバック条件、前バージョン、バックアップ、責任者、作業時間

9. 練習の進め方

最初の練習は、公開リポジトリや業務リポジトリではなく、空の検証リポジトリで行う。2つのローカルcloneまたは2つのブランチから同じ行を変更し、意図的にコンフリクトを発生させ、解消・abort・revertを試す

  1. 検証用リポジトリを作成し、初期ファイルをcommit
  2. 2本の作業ブランチで同じ行を別の内容へ変更
  3. mergeで競合を発生させ、内容を統合してcommit
  4. 別の小さなcommitを作り、revertで打ち消す
  5. 個人ブランチだけでrebase --abortまで試す
  6. PRを作成し、レビューコメント、修正push、CI確認、マージを記録
