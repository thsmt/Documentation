Terraform / Chapter 1–3

Terraform AWS運用リファレンス

第1章〜第3章で扱った基本概念、Ubuntuへの導入、Docker演習、AWSでのWordPress環境構築を、2026年8月22日の作業ログを基に整理したものです。実際のパスワード、AWSアカウントID、接続元IP、リソースIDは記載していない

ℹ️ このページで押さえる全体像

Terraformは「何を作りたいか」をHCLで宣言し、Terraform Coreが依存関係を判断し、Providerを通してAWSやDockerなどのAPIを操作するツールです。基本の流れは 作成 → init → validate → plan → apply → 確認 → destroy

Terraformが動く仕組み

main.tf / HCL→Terraform Core→ RPC →Provider→ API →AWS・Dockerなど
実際のリソース→ API応答 →Provider→ RPC →Terraform Core→State・Output
構成要素役割
Terraform Core.tfを読み、Stateを参照し、依存関係グラフを作り、Planを実行する
RPCTerraform CoreとProviderプラグインが別プロセス間で通信する仕組み
ProviderAWS、Dockerなど各サービス固有のリソース定義と作成・参照・更新・削除処理を実装する
APIProviderがAWS APIやDocker APIを呼び出し、実際のインフラを変更する
StateTerraformのリソースアドレスと、実環境のリソースを対応付ける
ℹ️ DSL・宣言型・実行順序

Terraform languageはHCL構文を使う、インフラ構成用の宣言型DSLである。シェルスクリプトのように上から順番に命令を実行するのではなく、完成してほしい状態を記述する。aws_instance.web が aws_security_group.web.id を参照すると、Terraformが依存関係を検出して順序を決める

したがって、ブロックやファイルの記述順は原則として実行順になりません。ただし、リストの添字、文字列、式の意味まで「何でも同じ」になるわけではありません。参照で表せない隠れた依存関係に限り、depends_onを使う

構築の流れ（本書53ページ相当）

  1. 作業場所を決める環境ごとにディレクトリとStateを分け、pwdとls -laを確認
  2. 構成を書くmain.tfなどに目的の状態を宣言
  3. 整形するterraform fmtで標準形式に
  4. 初期化するterraform initでProviderとBackendを準備
  5. 検証するterraform validateで構成の整合性を確認
  6. 計画するterraform planで追加・変更・削除・置換を確認
  7. 適用する問題がなければterraform applyまたは保存Planを適用
  8. 結果を確認するterraform output、terraform state list、クラウド側の画面やAPIで確認
  9. 変更を繰り返す構成修正後は再びfmt → validate → plan → applyを実行
  10. 片付ける不要になった検証環境はplan -destroyを確認後にdestroy

特に注意する記号は - と -/+ です。 置換には停止時間、IP変更、データ消失の可能性があります。件数だけでなく、各リソースの理由まで読んでから承認する

    docker = {

  name         = "nginx:latest"
  keep_locally = false

resource "docker_container" "nginx" {
  name  = "terraform-nginx"
  image = docker_image.nginx.image_id

    internal = 80
    external = 8000
  }

AWS Providerの認証と権限

AWS ProviderはAWS APIを呼び出すため、Terraformを実行する主体にIAM権限が必要です。Provider blockへアクセスキーを書かず、環境変数、共有credentials file、コンテナロール、EC2インスタンスプロファイルなどから認証情報を取得する

認証元用途ポイント
環境変数ローカル検証・一時的な切り替えAWS_ACCESS_KEY_ID、AWS_SECRET_ACCESS_KEY、必要に応じてAWS_SESSION_TOKENを使う
共有credentials fileAWS CLI profileとの共用~/.aws/credentialsとAWS_PROFILEを使う
EC2インスタンスプロファイルEC2上のTerraformIMDSから有効期限付きの一時認証情報を自動取得します。AWSの推奨方式
ℹ️ 認証情報の優先順位

AWS Providerでは環境変数がEC2インスタンスプロファイルより先に評価されます。したがって、IAMユーザーのアクセスキーを試すためにEC2ロールを外す必要はありません。AWS_EC2_METADATA_DISABLED=trueを追加すると、検証中にIMDSへフォールバックしないことも明示できる

⚠️ bootstrapの順番

TerraformでIAMユーザーを作る処理そのものにもiam:CreateUserやiam:AttachUserPolicyが必要です。先にEC2ロールを外すと作成できません。現在のEC2ロールを使う専用ディレクトリと専用Stateでユーザーを作成し、その後に認証方法を切り替える

IAMユーザーとアクセスキーを作るmain.tf

ℹ️ 提示コードで作成できるもの

IAMユーザー、アクセスキー、EC2の参照専用inline policyを作成できます。構文の考え方は正しいですが、ec2:Describe*は参照専用です。EC2、Security Group、EIP、RDSを作成する現在のWordPress構成をterraform applyする権限はない

bootstrap-iam/main.tf
terraform {
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "ap-northeast-1"

  default_tags {
    tags = {
      ManagedBy   = "Terraform"
      Environment = "learning"
    }
  }
}

resource "aws_iam_user" "terraform_operator" {
  name          = "terraform-wordpress-operator"
  path          = "/system/"
  force_destroy = false

  tags = {
    Purpose = "Terraform learning"
    Owner   = "<YOUR_NAME>"
  }
}

resource "aws_iam_access_key" "terraform_operator" {
  user = aws_iam_user.terraform_operator.name
}

data "aws_iam_policy_document" "terraform_operator_ec2_read_only" {
  statement {
    sid       = "DescribeEC2"
    effect    = "Allow"
    actions   = ["ec2:Describe*"]
    resources = ["*"]
  }
}

resource "aws_iam_user_policy" "terraform_operator_ec2_read_only" {
  name   = "terraform-ec2-describe"
  user   = aws_iam_user.terraform_operator.name
  policy = data.aws_iam_policy_document.terraform_operator_ec2_read_only.json
}

output "iam_user_name" {
  value = aws_iam_user.terraform_operator.name
}

output "aws_access_key_id" {
  value     = aws_iam_access_key.terraform_operator.id
  sensitive = true
}

output "aws_secret_access_key" {
  value     = aws_iam_access_key.terraform_operator.secret
  sensitive = true
}

ユーザーが変更する値

指定値例説明
terraform_operatorTerraform内のローカル名AWS上の名前ではない。変更する場合は、すべてのaws_iam_user.terraform_operatorなどの参照も同じ名前へ変更する。通常はそのままでよい
nameterraform-wordpress-operatorAWS上に作成されるIAMユーザー名です。同一AWSアカウント内で重複しない名前へ変更する
path/system/IAMユーザーを論理的に分類するパスです。先頭と末尾を/にします。不要なら/を使用できる
Purpose、Ownerタグのキーと値管理・検索・費用管理用の任意メタデータです。権限そのものには影響しません。<YOUR_NAME>を管理者名や識別名へ変更する
sidDescribeEC2IAM policy statementの識別名です。任意ですが、英数字で目的が分かる名前にする
actionsec2:Describe*許可するAWS API操作です。この例はEC2の参照操作だけです。作成・更新・削除権限はない
resources*権限の対象リソースです。EC2のDescribe系APIは個別ARNへ限定できない操作が多いため、この例では全リソースを指定する
policyのnameterraform-ec2-describeIAMユーザーへ直接埋め込むinline policy名です。用途が分かる名前へ変更できる
Providerのregionap-northeast-1Terraformが操作する既定リージョンです。IAMはグローバルサービスですが、EC2やRDSなどの操作先を決めるために指定する

現在のWordPress構成をapplyする場合

⚠️ ec2:Describe*だけでは構築できない

認証の切り替え確認だけなら上記inline policyで十分です。現在の第3章を構築する場合はEC2・VPC・Security Group・EIP・RDSなどの作成・更新・削除権限が必要です。学習環境では、上記のaws_iam_policy_documentとaws_iam_user_policyを削除し、次のattachmentへ置き換える

WordPress構築用の検証権限
resource "aws_iam_user_policy_attachment" "terraform_operator_power_user" {
  user       = aws_iam_user.terraform_operator.name
  policy_arn = "arn:aws:iam::aws:policy/PowerUserAccess"
}

PowerUserAccessは広い権限を持つAWS managed policyであり、最小権限ではありません。学習後はCloudTrailやIAM Access Analyzerで必要な操作を確認し、対象サービス・操作・リソースを限定したカスタマー管理ポリシーへ置き換える

リージョン変更で起きた置換事故

⚠️ リージョン変更による置換

ap-northeast-3で作成済みのStateを持ったままProviderをap-northeast-1へ変えると、SubnetやENIなどが大量の-/+になった。東京リージョンからは大阪リージョンのVPC IDが見つからず、InvalidVpcID.NotFoundになり、RDSのサービス管理ENIも手動では切り離せなかった

正しい考え方: 元のリージョンへ設定を戻し、元のStateで既存リソースを安全に削除または移行計画を立てます。その後、新リージョンは別ディレクトリ・別Stateで構築します。リージョン文字列だけを変更してapplyしない

既存ネットワークを参照する構成

main.tf
provider "aws" {
  region = "ap-northeast-1"
}

data "aws_vpc" "existing" {
  id = "<VPC_ID>"
}

data "aws_subnet" "public_1a" {
  id = "<PUBLIC_SUBNET_ID>"
}

resource "aws_security_group" "web" {
  name   = "terraform-wordpress-web-sg"
  vpc_id = data.aws_vpc.existing.id
}

resource "aws_instance" "web" {
  ami                         = "<AMI_ID_IN_THE_SAME_REGION>"
  instance_type               = "t2.micro"
  subnet_id                   = data.aws_subnet.public_1a.id
  associate_public_ip_address = true
  vpc_security_group_ids      = [aws_security_group.web.id]
  user_data                   = file("${path.module}/wordpress.sh")
}

Data Sourceで参照した既存VPC・SubnetはTerraformの作成・削除対象ではありません。Terraformが新規管理するSecurity Group、EC2、EIP、RDSなどと、手動作成済みネットワークの境界を明確にできる

実行ログから得た再発防止メモ

  • terraformだけでヘルプと利用可能なサブコマンドを確認できる
  • terraform fmt、validate、planは役割が異なるため、毎回すべて実行する
  • Providerブロックのリージョンと、AMI・VPC・Subnet・Key Pairのリージョンを揃える
  • Stateは作業ディレクトリに結び付くため、実行前にpwdを確認する
  • terraform state listで現在の管理対象を確認してから、applyやdestroyを行う
  • ViのSwap警告が出たら、別セッションの編集有無を確認し、内容を回復または保存してから不要なSwapを削除する
  • timedatectl set-timezone Asia/Tokyoが正しいコマンド
  • printenvが正しく、prinenvではない
  • 実際の出力にパスワードが出た場合、その値は漏えい扱いでローテーションを検討する
