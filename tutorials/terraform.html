Terraform / AWS

Terraform AWS運用リファレンス

Terraformの仕組み、実行環境へのインストール、構成ファイルと生成ファイル、AWS Providerの認証、AWSリソースの記述、エラー対処を整理する

Terraformとは

Terraformは、サーバー、ネットワーク、データベース、IAMなどのインフラ構成をコードで定義し、作成・変更・削除するInfrastructure as Code（IaC）ツールである。HCLで「どのような状態にしたいか」を宣言し、Terraformがリソース間の依存関係と実行順序を判断する

STEP 1

構成ファイル（HCL）

resource、data、providerなどのブロックで目標の構成を定義する

→読み込み
STEP 2

Terraform Core

同じディレクトリにある構成を読み、Stateと実環境を照合して依存関係と変更内容を計算する

→RPC
STEP 3

AWS Provider

Terraform CoreとAWS APIを接続するプラグイン。AWS固有のリソースと作成・参照・更新・削除処理を実装する

→AWS API
STEP 4

AWSリソース

VPC、Subnet、Security Group、EC2、EIP、RDSなど、ProviderがAPI経由で作成・変更・削除する実際のインフラ

State ─ Terraform Coreが読み書きする管理記録

Terraformのリソースアドレスと実際のリソースID・属性を対応付ける。CoreはStateと実環境を照合し、apply完了後の情報をStateへ反映する

ℹ️ Terraformが行う比較

planでは構成ファイルの目標状態、Stateに記録された管理状態、Providerが取得した実環境を比較して変更案を作る。applyではその変更をProvider経由でAPIへ送り、完了後の情報をStateへ反映する

Terraformのインストール

Terraform CLIは、terraformコマンドを実行する環境へインストールする。管理用のVMやEC2からAWSを操作する場合は、そのVMやEC2へのインストールが必要である。Terraformが作成する対象サーバーへTerraform自体をインストールする必要はない

Ubuntu／DebianのVMを実行環境にする場合は、HashiCorpのGPGキーと公式APTリポジトリを登録してTerraform CLIをインストールする。CI/CDやHCP Terraformでリモート実行する場合は、Terraformを実行するRunner側の環境とバージョンを管理する

Ubuntu / Debian
sudo apt-get update && sudo apt-get install -y gnupg software-properties-common

wget -O- https://apt.releases.hashicorp.com/gpg \
  | gpg --dearmor \
  | sudo tee /usr/share/keyrings/hashicorp-archive-keyring.gpg > /dev/null

gpg --no-default-keyring \
  --keyring /usr/share/keyrings/hashicorp-archive-keyring.gpg \
  --fingerprint

echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(grep -oP '(?<=UBUNTU_CODENAME=).*' /etc/os-release || lsb_release -cs) main" \
  | sudo tee /etc/apt/sources.list.d/hashicorp.list

sudo apt update
sudo apt-get install terraform

インストール確認

user shell
terraform version
command -v terraform
terraform -help
terraform plan -help

コマンド補完

Bash
touch ~/.bashrc
terraform -install-autocomplete
exec "$SHELL"

Terraformの構成ファイルと生成ファイル

Terraformは、実行ディレクトリ直下にあるすべての.tfファイルを1つのRoot Moduleとして読み込む。処理順はファイル名や記述順ではなく、ブロック間の参照関係から決まる。小規模な検証ではmain.tfだけでもよいが、実務では役割別に分けると管理しやすい

デプロイ前に用意するファイル

ファイル役割Git管理
terraform.tfTerraform本体とProviderのバージョン制約、Providerの取得元を定義含める
providers.tfAWSリージョン、Alias、共通タグなどProviderの設定を定義。アクセスキーは直接記述しない含める
main.tfresource、data、moduleなど、管理するインフラ本体を定義含める
variables.tf入力変数の型、説明、既定値、検証条件を定義含める
terraform.tfvars／*.auto.tfvars環境ごとの変数値を設定。パスワードやアクセスキーを含む場合はGitへ登録しない機密値を含まない場合のみ
outputs.tf作成後に参照するIPアドレス、DNS名、IDなどの出力を定義含める
backend.tfStateの保存先とロック方式を定義。S3などのRemote Backendを利用する場合に作成含める。ただし認証情報は書かない
wordpress.shなどfile()やtemplatefile()から参照するUser Data・テンプレート。参照している場合はデプロイに必要原則として含める

コマンド実行で生成・更新されるファイル

ファイル・ディレクトリ生成タイミング役割と取扱い
.terraform/terraform initProvider、Module、Backend情報を保持する作業用ディレクトリ。自動生成されるためGitへ登録しない
.terraform.lock.hclterraform init選択されたProviderのバージョンとハッシュを固定する。チームやCIで同じProviderを利用するためGitへ登録する
tfplanなどの保存済みPlanterraform plan -out=tfplan-outを指定した場合だけ生成される。構成・変数・機密値を含み得るためGitへ登録せず、適用後は不要なファイルを削除する
terraform.tfstateLocal Backendでterraform apply管理対象の現在状態を記録する重要ファイル。機密値を含み得るためGitへ登録しない。Remote Backendでは通常ローカルに保存しない
terraform.tfstate.backupLocal State更新時更新前のStateを保持するバックアップ。Stateと同様に機密情報として扱い、Gitへ登録しない
ℹ️ planとapplyで生成されるもの

通常のterraform planは結果を画面に表示するだけでPlanファイルを作らない。-outを指定した場合だけ保存済みPlanが作られる。applyはAWSリソースを変更し、Local BackendではStateを作成または更新するが、main.tfなどの構成ファイルは自動生成しない

Terraform CLIコマンドリファレンス

コマンド用途運用上の確認点
terraform versionTerraform本体と実行環境を表示チームやCIで利用するバージョンと一致させる
terraform fmtHCLを標準形式へ整形変更後に実行し、差分を確認
terraform initProvider、Module、Backendを初期化作業ディレクトリごとに最初に実行
terraform init -upgrade制約内でProviderを再選択lock fileとの差分とProviderの更新内容を確認
terraform validate構成の構文・参照・引数を検証認証やAWS上の権限までは検証しない
terraform providers構成とStateが必要とするProviderを表示想定外のProviderや古い参照がないか確認
terraform plan適用予定の差分を表示追加・更新・削除・置換を確認
terraform plan -out=tfplanPlanをファイルへ保存レビューしたPlanをそのまま適用する場合に使用
terraform show tfplan保存したPlanを表示apply前の最終確認に使用
terraform apply tfplan保存済みPlanを適用Plan作成後の構成変更や認証先変更を避ける
terraform applyPlan作成後に変更を適用yes入力前に対象と件数を確認
terraform output定義済みoutputを表示機密値は画面やログへ残さない
terraform state listStateの管理対象を一覧表示作業ディレクトリとStateが正しいか確認
terraform state show <ADDRESS>State内の1リソースを表示機密属性が含まれる可能性に注意
terraform import既存リソースをStateへ関連付け先に対応するresourceブロックを作成
terraform plan -destroy削除予定を事前表示削除・再作成・データ保持条件を確認
terraform destroy管理対象を削除同じBackend、State、AWSアカウント、リージョンで実行

Planの記号

記号意味確認点
+新規作成作成先アカウント、リージョン、名前、費用
-削除データ消失、依存先、復旧方法
~既存リソースを更新停止や再起動の有無
-/+削除後に再作成ID・IP・エンドポイント変更と停止時間
<=Data Sourceを読み取り参照先のアカウントとリージョン
(known after apply)適用完了後に確定未知値そのものはエラーではない

AWS Providerとresourceブロック

terraformブロックでProviderの配布元とバージョン制約を宣言し、providerブロックでAWSリージョンなどの接続設定を指定する。Providerのバージョンはproviderブロックへ書かず、required_providersへ指定する

terraform.tf
terraform {
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
main.tf
provider "aws" {
  region = "ap-northeast-1"

  default_tags {
    tags = {
      ManagedBy   = "Terraform"
      Environment = "stg"
      Project     = "WordPress"
    }
  }
}
❌ required_providersはRoot Module内で1か所

main.tfとterraform.tfの両方にrequired_providersを定義すると、Duplicate required providers configurationになる。ファイル名ではなく、同じディレクトリにあるすべての*.tfが1つのRoot Moduleとして読み込まれる

resourceブロックの読み方

基本構文
resource "aws_instance" "web" {
  ami           = "<AMI_ID_IN_AP_NORTHEAST_1>"
  instance_type = "t2.micro"
}
記述意味
resourceTerraformが作成・更新・削除を管理するリソース
aws_instanceAWS Providerが定義するリソースタイプ
webTerraform構成内だけで使うローカル名
aws_instance.webほかのブロックから参照するリソースアドレス
amiなどリソースタイプ固有の引数

既存VPC・Subnetを参照するData Source

network.tf
data "aws_vpc" "existing" {
  id = "<VPC_ID>"
}

data "aws_subnet" "public_1a" {
  id = "<PUBLIC_SUBNET_ID>"
}

data "aws_subnet" "private_1a" {
  id = "<PRIVATE_SUBNET_1A_ID>"
}

data "aws_subnet" "private_1c" {
  id = "<PRIVATE_SUBNET_1C_ID>"
}

Data Sourceで参照したVPC・Subnetは、参照しただけではTerraformの削除対象にならない。新規作成したresourceと既存ネットワークの管理境界を明確にする

AWS Providerへの認証情報の付与

AWS ProviderがAPIを呼び出すには、認証情報とIAM権限の両方が必要になる。アクセスキーやIAMロールは「誰として実行するか」を決め、IAMポリシーは「何を操作できるか」を決める

認証方法の比較

番号認証方法主な利用場所評価要点
1IAMロールEC2、ECS、Lambda推奨AWSが有効期限付きの一時認証情報を提供する。長期アクセスキーの配布が不要
2OIDCなどによるAssumeRoleCI/CD推奨ジョブごとに一時認証情報を取得できる
3IAM Identity CenterまたはAssumeRole人が操作する端末推奨フェデレーションと一時認証情報を利用できる
4名前付きAWS CLIプロファイルローカル検証条件付きで推奨複数のAWSアカウントやRoleを切り替えやすい
5環境変数短時間の動作確認一時利用のみ現在のシェルだけへ設定し、作業後に解除する
6IAMユーザーの長期アクセスキーRoleを利用できない例外原則非推奨保管、失効、ローテーションの運用が必要
7Providerブロックへの直接記述利用しない非推奨構成ファイルやバージョン管理から認証情報が漏えいする危険がある
認証方式を選ぶ基準

有効期限付きの一時認証情報を取得できる方式を優先する。切り替えやエラー調査では、環境変数、名前付きプロファイル、IAMロールを同時に混在させず、aws sts get-caller-identityで実行主体を確認する。実際の認証情報はTerraform構成やバージョン管理へ保存しない

Providerブロックへの直接指定（非推奨）

非推奨の例
provider "aws" {
  region     = "ap-northeast-1"
  access_key = "<AWS_ACCESS_KEY_ID>"
  secret_key = "<AWS_SECRET_ACCESS_KEY>"
}
⚠️ .tfへアクセスキーを書かない

この方式はProviderへ認証情報を渡す仕組みを理解しやすい一方、Git、バックアップ、画面共有、レビュー、ログなどから長期認証情報が漏えいする危険がある。実際のアクセスキーをmain.tfやterraform.tfvarsへ直接記述しない

EC2インスタンスプロファイル（推奨）

Terraformを実行するEC2へIAMロールを割り当てると、AWS ProviderはIMDSから一時認証情報を自動取得する。Providerブロックにはリージョンなどの非機密設定だけを記述する

main.tf
provider "aws" {
  region = "ap-northeast-1"
}
認証主体を確認
aws sts get-caller-identity
aws configure list
printenv | grep '^AWS_' || true

名前付きプロファイル

ローカル端末
aws configure --profile terraform-dev
export AWS_PROFILE="terraform-dev"
export AWS_DEFAULT_REGION="ap-northeast-1"

aws sts get-caller-identity
aws configure list
terraform plan

AWS_PROFILEを設定すると、~/.aws/credentialsまたは~/.aws/configの名前付きプロファイルを選択できる。環境変数のアクセスキーが同時に設定されている場合は、環境変数がプロファイルより優先される

環境変数（短時間の検証）

現在のシェルだけに設定
set +o history

export AWS_ACCESS_KEY_ID="<CSVにあるアクセスキー>"
export AWS_SECRET_ACCESS_KEY="<CSVにあるシークレットアクセスキー>"
export AWS_DEFAULT_REGION="ap-northeast-1"
export AWS_EC2_METADATA_DISABLED="true"

aws sts get-caller-identity
aws configure list
terraform plan

unset AWS_ACCESS_KEY_ID
unset AWS_SECRET_ACCESS_KEY
unset AWS_SESSION_TOKEN
unset AWS_DEFAULT_REGION
unset AWS_EC2_METADATA_DISABLED

set -o history

AWS_EC2_METADATA_DISABLED=trueを指定すると、検証中にEC2のIMDSへフォールバックしない。環境変数は現在のシェルにだけ設定し、シェル初期化ファイルへ長期アクセスキーを保存しない

IAMポリシーでAWS操作を許可する

認証に成功しても、実行主体へ必要なIAM権限がなければUnauthorizedOperationやAccessDeniedになる。EC2、VPC、Security Group、EIP、RDSなど、Terraformが実行するAPI操作をIAMポリシーで許可する

検証用の広い権限
resource "aws_iam_user" "terraform_operator" {
  name = "terraform-wordpress-operator"
  path = "/system/"
}

resource "aws_iam_user_policy_attachment" "terraform_operator_power_user" {
  user       = aws_iam_user.terraform_operator.name
  policy_arn = "arn:aws:iam::aws:policy/PowerUserAccess"
}

AWSエラーの対処法

エラー発生時は、Terraformの構文だけでなく、実行ディレクトリ、State、認証主体、AWSアカウント、リージョン、IAM権限を順に切り分ける

エラー・症状主な原因対処
No valid credential sources found環境変数、Profile、IAMロールのいずれからも認証情報を取得できないaws configure listとaws sts get-caller-identityで認証元を確認
UnauthorizedOperation／AccessDenied認証には成功したがIAM権限が不足エラー内のAction、CloudTrail、IAM Policy Simulatorを確認し、必要な権限を追加
InvalidAMIID.NotFoundAMI IDとProviderのリージョンが不一致対象リージョンでAMIを検索し、AMI IDを変更
InvalidVpcID.NotFoundVPC IDとProviderのリージョンまたはAWSアカウントが不一致Caller Identity、リージョン、VPC IDを同時に確認
Duplicate required providers configuration同じRoot Moduleにrequired_providersが複数存在main.tfまたはterraform.tfの1か所へ統合
Provider lock不一致構成のversion制約と.terraform.lock.hclの選択が不一致制約を確認後、必要な場合だけterraform init -upgradeを実行
大量の-/+リージョン、Subnet、名前などForceNew属性を変更applyを中止し、元の設定とStateを確認。新リージョンは別Backend・別Stateで構築
RDS ENIを削除できないRDSが管理するENIをSubnet削除より先に外そうとしているRDS削除完了後にDB Subnet Group、Subnetの順で削除。ENIを手動で切り離さない
別ディレクトリで対象なし異なるBackendまたはローカルStateを参照pwd、Backend設定、terraform state listを確認
