RHEL 9 Apache TLS構築

EC2上のRed Hat Enterprise Linux 9.8へApache HTTP Serverを導入し、書籍の手順に合わせてEC P-256秘密鍵とCSRを作成した実機記録から、自己署名証明書によるHTTPS終端、DNS、通信確認までを整理する

作業再開時の最優先事項

実機では秘密鍵の確認時にpriv:を含む出力を画面へ表示している。この秘密鍵は証明書の発行前に必ず再生成し、CSRも新しい鍵から作り直す。本文には秘密鍵の内容、秘密鍵を表示するコマンド、SSH接続元IP、EC2の固定されていないパブリックIPv4を掲載しない

記録の範囲

「実施済み」は2026年8月12日の実行ログで確認した範囲、「この後の手順」は未実施の設計値である。ApacheのVirtualHost作成、自己署名証明書の発行、サービス起動、Security Group、Route 53、ブラウザ確認は、実機での実行後に結果を追記する

証明書発行の流れ

  1. サーバー内での秘密鍵生成
  2. 秘密鍵に対応する公開鍵と申請者情報を含むCSR生成
  3. 公開CA利用時のCSR提出。秘密鍵は提出対象外
  4. CAによるドメイン管理権限や申請者情報の検証
  5. CAからのサーバー証明書と中間証明書の受領
  6. 秘密鍵、サーバー証明書、必要な証明書チェーンのApache設定
  7. 鍵の対応、SAN、有効期限、Apache構文、実際のTLS通信の確認

自己署名証明書では手順3から5の公開CAを使わず、CSRを同じ秘密鍵で署名する。暗号化通信はできるが、クライアントが発行者を信頼していないためブラウザ警告が表示される。公開サービスの最終構成には使用しない

ACMのエクスポート可能なパブリック証明書は、このページで作成したCSRをACMへ提出する方式ではない。ACMでwww.zexample.comを申請し、DNS検証後にACMが管理する鍵と証明書をエクスポートする

AWS公式手順：ACM - Request a public certificate

実行履歴上の訂正

この後1：秘密鍵とCSRの再生成

表示済みの秘密鍵を証明書へ使用しない。まだ証明書を発行していないため失効処理は不要であり、新しいEC P-256鍵へ交換してCSRを作り直す

一時ファイルへ新しい秘密鍵を生成する

shell
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out /etc/pki/tls/private/www.zexample.com.key.new

新しい秘密鍵の権限を設定する

shell
chmod 600 /etc/pki/tls/private/www.zexample.com.key.new

秘密値を表示せず、新しい秘密鍵が正常に読めることを確認する

shell
openssl pkey -in /etc/pki/tls/private/www.zexample.com.key.new -check -noout

確認済みの新しい秘密鍵で、表示済みの秘密鍵を置き換える

shell
mv -f /etc/pki/tls/private/www.zexample.com.key.new /etc/pki/tls/private/www.zexample.com.key

置換後の秘密鍵の所有者とグループをrootへ固定する

shell
chown root:root /etc/pki/tls/private/www.zexample.com.key

書籍と同じ対話式コマンドでCSRを再生成し、既存CSRを置き換える

shell
openssl req -new -key /etc/pki/tls/private/www.zexample.com.key -out /etc/pki/tls/private/www.zexample.com.csr

再生成したCSRの署名を確認する

shell
openssl req -noout -verify -in /etc/pki/tls/private/www.zexample.com.csr

この後2：CSR提出先を選ぶ

選択肢CSRの扱い受け取るもの用途
今回の自己署名外部へ提出せず、同じ秘密鍵で署名自己署名CRT2026年8月末までのサーバー内TLS検証
公開CACAの管理画面またはAPIへSAN付きCSRを提出サーバー証明書と中間証明書一般ブラウザから信頼される公開サービス
ACMエクスポートこのCSRは使わない。ACMでFQDNを申請証明書、暗号化された秘密鍵、証明書チェーン後続の自動更新検証

CAへのCSR提出方法に共通コマンドはない。利用する認証局の管理画面で「サーバー証明書」「CSR貼り付け」などを選び、-----BEGIN CERTIFICATE REQUEST-----から-----END CERTIFICATE REQUEST-----までを提出する。秘密鍵ファイルは送信しない

公開CAへ提出する場合は、SANを含むCSRを別ファイルとして生成する。次は書籍の対話式コマンドにSAN拡張だけを追加した例である

shell
openssl req -new -key /etc/pki/tls/private/www.zexample.com.key -out /etc/pki/tls/private/www.zexample.com-public-ca.csr -addext "subjectAltName=DNS:www.zexample.com"

CAへ送る前にCSRのSANと署名を確認する

shell
openssl req -in /etc/pki/tls/private/www.zexample.com-public-ca.csr -noout -verify -text

出典：Red Hat - Creating and managing TLS keys and certificates

この後3：自己署名証明書を発行

対話式CSRにはSANが含まれていないため、署名時にサーバー証明書用の拡張を追加する。EC鍵では鍵交換用のkeyEnciphermentではなく、署名用のdigitalSignatureを指定する

/etc/pki/tls/certs/www.zexample.com.ext
tee /etc/pki/tls/certs/www.zexample.com.ext >/dev/null <<'EOF'
[server_cert]
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature
extendedKeyUsage = serverAuth
subjectAltName = DNS:www.zexample.com
subjectKeyIdentifier = hash
EOF

CSRを同じEC秘密鍵で自己署名する。20260831145959Zは2026年8月31日14時59分59秒UTCであり、日本時間の8月31日23時59分59秒に相当する。-not_afterはOpenSSL 3.5で利用できる

実機のOpenSSLが3.5系であることを再確認する

shell
openssl version

x509サブコマンドが期限の直接指定に対応していることを確認する

shell
openssl x509 -help 2>&1 | grep -E -- '-not_before|-not_after'
shell
openssl x509 -req -in /etc/pki/tls/private/www.zexample.com.csr \
  -key /etc/pki/tls/private/www.zexample.com.key \
  -sha256 \
  -set_serial 0x01 \
  -not_before today \
  -not_after 20260831145959Z \
  -extfile /etc/pki/tls/certs/www.zexample.com.ext \
  -extensions server_cert \
  -out /etc/pki/tls/certs/www.zexample.com.crt

出典：OpenSSL 3.5 - openssl-x509

証明書とCSRの権限を整える。秘密鍵は0600のまま維持する

shell
chmod 644 /etc/pki/tls/private/www.zexample.com.csr /etc/pki/tls/certs/www.zexample.com.crt /etc/pki/tls/certs/www.zexample.com.ext

RHEL既定のSELinuxコンテキストをDocumentRoot、秘密鍵、証明書へ適用する

shell
restorecon -RFv /var/www/www.zexample.com /etc/pki/tls/private/www.zexample.com.key /etc/pki/tls/private/www.zexample.com.csr /etc/pki/tls/certs/www.zexample.com.crt /etc/pki/tls/certs/www.zexample.com.ext

この後4：証明書とEC鍵を確認

証明書のSubject、Issuer、シリアル番号、有効期間、SHA-256フィンガープリント、SANなどを表示する。自己署名ではSubjectとIssuerが同じになる

shell
openssl x509 -in /etc/pki/tls/certs/www.zexample.com.crt -noout -subject -issuer -serial -dates -fingerprint -sha256 -ext subjectAltName,basicConstraints,keyUsage,extendedKeyUsage

証明書がwww.zexample.comに一致することを確認する

shell
openssl x509 -in /etc/pki/tls/certs/www.zexample.com.crt -noout -checkhost www.zexample.com

自己署名証明書を自身のトラストアンカーとして署名検証する

shell
openssl verify -CAfile /etc/pki/tls/certs/www.zexample.com.crt /etc/pki/tls/certs/www.zexample.com.crt

EC秘密鍵から公開鍵をDER形式で取り出し、SHA-256を計算する

shell
openssl pkey -in /etc/pki/tls/private/www.zexample.com.key -pubout -outform DER | openssl dgst -sha256

CSRから同じ形式の公開鍵を取り出し、SHA-256を計算する

shell
openssl req -in /etc/pki/tls/private/www.zexample.com.csr -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst -sha256

証明書から同じ形式の公開鍵を取り出し、SHA-256を計算する。3つの結果が完全に一致すれば、秘密鍵、CSR、証明書が対応している

shell
openssl x509 -in /etc/pki/tls/certs/www.zexample.com.crt -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst -sha256
業務手順のハッシュ値との違い

openssl rsa -modulusとopenssl x509 -modulusの比較はRSA鍵向けであり、今回のEC鍵には使用しない。-subject_hashと-issuer_hashは証明書をSubject名またはIssuer名で検索するための索引値で、鍵と証明書の整合性を示すハッシュではない

業務記録としてSubject名の索引値を取得する場合は次を実行する

shell
openssl x509 -subject_hash -noout -in /etc/pki/tls/certs/www.zexample.com.crt

Issuer名の索引値を取得する場合は次を実行する

shell
openssl x509 -issuer_hash -noout -in /etc/pki/tls/certs/www.zexample.com.crt

この後5：ApacheでHTTPS終端

HTTPのVirtualHostはHTTPSへ301リダイレクトし、HTTPSのVirtualHostで自己署名証明書を使ってTLS終端する。設定ファイル名を00-から始め、同じIP・ポートの既定VirtualHostとして先に読み込ませる

/etc/httpd/conf.d/00-www.zexample.com.conf
tee /etc/httpd/conf.d/00-www.zexample.com.conf >/dev/null <<'EOF'
<VirtualHost *:80>
  ServerName www.zexample.com
  Redirect permanent / https://www.zexample.com/
</VirtualHost>

<VirtualHost *:443>
  ServerName www.zexample.com
  DocumentRoot /var/www/www.zexample.com/public_html

  SSLEngine on
  SSLCertificateFile /etc/pki/tls/certs/www.zexample.com.crt
  SSLCertificateKeyFile /etc/pki/tls/private/www.zexample.com.key

  <Directory "/var/www/www.zexample.com/public_html">
    Options -Indexes
    AllowOverride None
    Require all granted
  </Directory>

  ErrorLog /var/log/httpd/www.zexample.com-error.log
  CustomLog /var/log/httpd/www.zexample.com-access.log combined
</VirtualHost>
EOF

VirtualHost設定へRHEL既定のSELinuxコンテキストを適用する

shell
restorecon -v /etc/httpd/conf.d/00-www.zexample.com.conf

公開CAからリーフ証明書と中間証明書を受領した場合は、リーフを先頭、中間証明書を後ろに連結したfull chainを作成する

shell
cat /etc/pki/tls/certs/www.zexample.com-leaf.crt /etc/pki/tls/certs/<INTERMEDIATE_CA_FILE> > /etc/pki/tls/certs/www.zexample.com.fullchain.pem

公開CAへ切り替えた後はSSLCertificateFileをfull chainへ変更する。Apache 2.4.8以降は中間証明書をSSLCertificateFileへ含められるため、旧式のSSLCertificateChainFileは使用しない

この後9：ローカル、外部、ブラウザ確認

サーバー内からHostヘッダーを指定し、HTTPがHTTPSへ301リダイレクトされることを確認する

shell
curl -I -H 'Host: www.zexample.com' http://127.0.0.1/

DNSを経由せず、ローカルの443番へSNIとHostを指定してHTTPSコンテンツを確認する。自己署名証明書の検証を一時的に省略するため、検証時だけ-kを使う

shell
curl -vk --resolve www.zexample.com:443:127.0.0.1 https://www.zexample.com/

外部からHTTPの301リダイレクトを確認する

shell
curl -I http://www.zexample.com/

外部から自己署名証明書の提示内容とHTTPS応答を確認する

shell
curl -vkI https://www.zexample.com/

SNIを指定して、Apacheが実際に提示する証明書チェーン、Subject、Issuer、有効期間を確認する

shell
openssl s_client -connect www.zexample.com:443 -servername www.zexample.com -showcerts </dev/null

ブラウザでhttps://www.zexample.com/を開く。自己署名段階では発行者を信頼できない警告が表示されることが想定結果であり、本番利用者へ警告の回避操作を案内しない。公開CAまたはACMエクスポート証明書へ交換後は、ブラウザ警告が消え、次のコマンドが-kなしで成功することを確認する

shell
curl -I https://www.zexample.com/
