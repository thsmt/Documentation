EventBridge Scheduler

EventBridge SchedulerによるEC2・RDS・WorkSpacesなどの自動停止・起動の構築手順（IAMポリシー、実行ロール、Schedule作成）をまとめる
作成後の監視・通知・トラブルシュートに必要なCloudWatch、SNS、DLQ、CloudTrailの確認方法を整理する

自動停止・起動を適用できる主なサービス

対象可否は「サービス名」ではなく「そのAPI操作がUniversal targetで利用可能か」「リソースが状態遷移をサポートするか」「実行ロールに権限があるか」で判断する

サービス停止または縮退API起動または復帰API用途と主な制約
Amazon EC2stopInstancesstartInstancesEBSルートボリュームのインスタンスに適用。停止中はパブリックIPv4アドレスが変わる場合がある
Amazon RDSstopDBInstance / stopDBClusterstartDBInstance / startDBClusterDBインスタンスとAurora・RDS Multi-AZ DBクラスターを同じAmazon RDSターゲットで操作する。停止可能な構成と7日後の自動起動を確認
Amazon DocumentDBstopDBClusterstartDBCluster開発・検証用途で停止可能。クラスター状態、料金、対応リージョンを事前確認
Amazon NeptunestopDBClusterstartDBCluster最大7日間停止可能。クラスターの復帰時間とアプリケーションの再接続を考慮
Amazon WorkSpacesstopWorkspacesstartWorkspacesAutoStopまたはManualの停止済みWorkSpaceを開始可能。1リクエストで最大25台を指定
Amazon RedshiftpauseClusterresumeCluster停止ではなく一時停止・再開。再開まで数分以上かかる場合があり、停止不可なクラスター条件がある
Amazon SageMakerstopNotebookInstancestartNotebookInstanceNotebookインスタンスを検証環境の夜間停止に使用する。セッション終了と接続中ユーザーへの影響を確認
Amazon LightsailstopInstancestartInstance停止・起動APIに対応。静的IPの割り当てと、停止中も発生する料金を確認
Amazon ECSupdateServiceでdesiredCountを0へ縮退updateServiceで復帰値を設定サービスのdesired countを変更する方式。復帰値を入力へ固定するため、状態を保持するワークフローを推奨
AWS Auto ScalingupdateAutoScalingGroupで容量を0へ縮退updateAutoScalingGroupで復帰値を設定最小・最大・希望容量を変更する方式。ほかのスケーリングポリシーとの競合を確認

カスタムIAMポリシーの作成

IAMコンソールでポリシーを作成を開き、JSONタブへ対象Scheduleに対応する許可ポリシーを貼り付けて作成する。停止用と起動用は別ポリシーとして管理する

ポリシー名: EC2InstanceStopPolicy

json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PolicyForStopEC2Instance",
    "Effect": "Allow",
    "Action": "ec2:StopInstances",
    "Resource": "*"
  }]
}

ポリシー名: EC2InstanceStartPolicy

json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PolicyForStartEC2Instance",
    "Effect": "Allow",
    "Action": "ec2:StartInstances",
    "Resource": "*"
  }]
}

⚠️ Resourceの範囲

上記はコンソール検証を進めやすくするためResourceを*としている。実運用では、停止を許可するEC2インスタンスARNだけへ制限する。RDSやWorkSpacesは同じポリシーへ混在させず、サービスと操作単位で権限を分離する

IAMロールの作成

次に、Schedulerが引き受ける実行ロールEventBridgeSchedulerEC2Stopを作成する
IAMコンソールでロールを作成を開き、カスタム信頼ポリシーを選択してScheduler用の信頼ポリシーを登録する

  1. IAMのロールを作成を開き、カスタム信頼ポリシーを選択
  2. 次の信頼ポリシーを登録
  3. 許可ポリシーとしてEC2InstanceStopPolicyをアタッチし、ロール名をEventBridgeSchedulerEC2Stopとして作成

実行ロールのカスタム信頼ポリシーは次のとおり

json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "scheduler.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}

Schedule作成手順

EC2を毎日18:00に停止する

東京リージョンのEC2インスタンス2台を対象として、毎日18:00 JSTに停止するScheduleをAWSマネジメントコンソールから作成する
Schedulerと対象EC2は同じリージョンに作成する

1. 停止前の状態を確認

対象となる2台が実行中であることを確認する。利用者接続、実行中バッチ、バックアップ、メンテナンス処理がある場合は、停止前に終了させる

2. Scheduleの詳細を指定

設定項目設定値
リージョンアジアパシフィック（東京）
Schedule名ec2-stop-daily-schedule
Scheduleグループec2-schedule-group
頻度定期的なSchedule
タイムゾーンAsia/Tokyo
種類cronベースのSchedule
cron式cron(0 18 * * ? *)
Flexible time windowOFF
開始日時・終了日時指定しない

3. Amazon EC2サービスを選択

Target APIですべてのAPIを選択する。サービス検索欄にAmazon EC2を入力し、表示されたAmazon EC2を選択する

4. StopInstances APIを選択

Amazon EC2のAPI一覧でstopInstancesを検索し、StopInstancesを選択する。停止処理用のScheduleでは、起動用のStartInstancesを選択しない

5. 停止対象のインスタンスIDを入力

Targetの入力欄に、停止対象のInstanceIds配列を指定する。IDはEC2コンソールからコピーし、停止対象以外のインスタンスを含めない

json
{
  "InstanceIds": [
    "<EC2_INSTANCE_ID_1>",
    "<EC2_INSTANCE_ID_2>"
  ]
}

6. 実行ロールを選択

Scheduleを有効化し、完了後のアクションはNONE、再試行はOFF、DLQはなし、暗号化はデフォルトとする。既存のロールを使用を選択し、EventBridgeSchedulerEC2Stopを指定する

確認画面でリージョン、実行時刻、Target、対象インスタンス、実行ロールを再確認してScheduleを作成する。最初の実行後は、EC2の状態とCloudTrailのStopInstancesイベントを確認する

EC2停止ScheduleをAWS CLIで作成

コンソールと同じ設定をAWS CLIで作成する場合は、Target定義とScheduleを次のように指定する

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/EventBridgeSchedulerEC2Stop",
  "Arn": "arn:aws:scheduler:::aws-sdk:ec2:stopInstances",
  "Input": "{\"InstanceIds\":[\"<EC2_INSTANCE_ID_1>\",\"<EC2_INSTANCE_ID_2>\"]}"
}
CloudShell
aws scheduler create-schedule \
  --name ec2-stop-daily-schedule \
  --group-name ec2-schedule-group \
  --schedule-expression "cron(0 18 * * ? *)" \
  --schedule-expression-timezone "Asia/Tokyo" \
  --flexible-time-window '{"Mode":"OFF"}' \
  --target file://target-ec2-stop.json \
  --state ENABLED

EC2起動Schedule

起動用は停止用と別のTarget定義と実行ロールを使用し、毎日09:00 JSTに設定する。起動後のアプリケーション初期化時間、EBSボリュームチェック、監視エージェントの起動時間を含めて時刻を決める

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/EventBridgeSchedulerEC2Start",
  "Arn": "arn:aws:scheduler:::aws-sdk:ec2:startInstances",
  "Input": "{\"InstanceIds\":[\"<EC2_INSTANCE_ID_1>\",\"<EC2_INSTANCE_ID_2>\"]}"
}
CloudShell
aws scheduler create-schedule \
  --name ec2-start-daily-schedule \
  --group-name ec2-schedule-group \
  --schedule-expression "cron(0 9 * * ? *)" \
  --schedule-expression-timezone "Asia/Tokyo" \
  --flexible-time-window '{"Mode":"OFF"}' \
  --target file://target-ec2-start.json \
  --state ENABLED

RDS DB instance停止・起動

RDSではDBInstanceIdentifierを入力に指定する。停止できない構成ではAPIが失敗するため、事前確認の結果とDLQを必ず確認する。停止状態を7日より長く維持する設計には向かない

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:rds:stopDBInstance",
  "Input": "{\"DBInstanceIdentifier\":\"<RDS_DB_INSTANCE_IDENTIFIER>\"}"
}
json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:rds:startDBInstance",
  "Input": "{\"DBInstanceIdentifier\":\"<RDS_DB_INSTANCE_IDENTIFIER>\"}"
}

Amazon WorkSpaces Personal停止・起動

WorkSpaces Personalは、単一または最大25台のWorkSpace IDをAPI入力に指定する。利用者が接続中の時間帯に停止すると業務影響があるため、通知、猶予時間、例外対象を運用設計に含める

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:workspaces:stopWorkspaces",
  "Input": "{\"StopWorkspaceRequests\":[{\"WorkspaceId\":\"<WORKSPACE_ID>\"}]}"
}
json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:workspaces:startWorkspaces",
  "Input": "{\"StartWorkspaceRequests\":[{\"WorkspaceId\":\"<WORKSPACE_ID>\"}]}"
}

モニタリング・通知・変更管理

Schedule作成後は、設定、呼び出し試行、Target APIの失敗、Targetリソースの状態、設定変更履歴を分けて確認する。設定内容はSchedulerコンソール、実行メトリクスと通知はCloudWatch、失敗理由はSQS DLQ、変更履歴はCloudTrail、実際の停止・起動結果はTargetサービスで確認する

Schedulerコンソールで設定を確認

  1. AWSマネジメントコンソールでAmazon EventBridgeを開き、ナビゲーションからScheduler ＞ スケジュールを選択
  2. Scheduleを作成したリージョンへ切り替え、ScheduleグループとSchedule名で対象を検索
  3. Scheduleの状態、スケジュール式、タイムゾーン、Flexible time window、Target ARN、Input、実行ロール、再試行、DLQ、暗号化設定を確認
  4. 時刻を変更する場合は編集を開き、今後10回の実行日時プレビューが意図した業務時刻になることを確認して保存
ℹ️ Schedulerコンソールだけでは完結しない

Schedulerコンソールは設定内容の確認に使用する。個々の呼び出しが成功したかを判断する完全な実行履歴画面ではないため、CloudWatchメトリクスとTargetサービスの状態を合わせて確認する

CloudWatchで実行状況をモニタリング

  1. CloudWatchコンソールでメトリクス ＞ すべてのメトリクス ＞ Schedulerを開く
  2. Scheduleごとの運用ではSchedule Group Metrics、リージョン全体の傾向ではAccount Metricsを選択
  3. Scheduleと同じリージョンを選択し、対象のSchedule Groupとメトリクスを選択
  4. グラフ化したメトリクスで統計をSum、期間をScheduleの実行間隔に合わせ、実行予定時刻の前後を表示
メトリクス確認できること増加時の初動
InvocationAttemptCountSchedulerがTargetの呼び出しを試行した回数0の場合はSchedule状態、cron式、タイムゾーン、開始・終了日時を確認
TargetErrorCountTarget APIが例外を返した回数実行ロール、Input、対象リソースの状態、DLQメッセージを確認
TargetErrorThrottledCountTargetサービスのAPIスロットリングで失敗した回数実行時刻の分散、再試行設定、Target側クォータを確認
InvocationThrottleCountScheduler側の呼び出しクォータで抑制された回数Scheduleの集中を避け、必要に応じてService Quotasを確認
InvocationDroppedCount再試行を使い切り、Target呼び出しを終了した回数DLQ、最大イベント保持時間、最大再試行回数を確認
InvocationsSentToDeadLetterCount失敗イベントをDLQへ正常に送信した回数SQSコンソールでメッセージを取得し、エラーコードと内容を確認
InvocationsFailedToBeSentToDeadLetterCount失敗イベントをDLQへ送信できなかった回数DLQ ARN、sqs:SendMessage、キューポリシー、KMSキーポリシーを確認
ℹ️ Schedule単位ではなくSchedule Group単位

AWS/SchedulerのディメンションはScheduleGroupであり、同じグループ内の複数Scheduleが集計される。Schedule単位で切り分ける必要がある場合は、グループ設計、DLQのSCHEDULE_ARN、CloudTrail、Targetサービスのイベントを組み合わせる

メトリクスはベストエフォートで配信されるため、完全な処理台帳としては扱わない。監視項目とGUIでの表示手順は、AWS公式手順：EventBridge SchedulerのCloudWatch監視

CloudWatchアラームとSNSで失敗を通知

失敗を人へ通知する場合は、SchedulerのエラーメトリクスをCloudWatchアラームで評価し、Amazon SNSトピックからメール、SMS、HTTPS、Lambdaなどの購読先へ配信する

  1. CloudWatchのすべてのメトリクス ＞ Scheduler ＞ Schedule Group Metricsで対象グループのTargetErrorCountを選択
  2. アクション ＞ アラームの作成を開き、統計をSum、しきい値を1以上に設定
  3. 欠落データは適正（しきい値を超えていない）として扱い、通常時にデータがないことによる誤通知を防止
  4. 通知先としてSNSトピックを選択または新規作成し、メール購読では受信した確認メールから購読を確定
  5. InvocationDroppedCountとInvocationsFailedToBeSentToDeadLetterCountにも同じ流れでアラームを作成
  6. 検証用の単発Scheduleで意図的に安全な失敗を発生させ、アラーム、SNS通知、DLQ格納までを確認
通知したい状態検知元通知経路
Target APIがエラーを返したTargetErrorCount >= 1CloudWatchアラーム → SNS
再試行を使い切ったInvocationDroppedCount >= 1CloudWatchアラーム → SNS
DLQへの保存にも失敗したInvocationsFailedToBeSentToDeadLetterCount >= 1CloudWatchアラーム → SNS
EC2が実際に停止または起動したEC2 Instance State-change NotificationEventBridgeルール → SNS
⚠️ 呼び出し試行と処理完了は別

InvocationAttemptCountはTarget APIを呼び出そうとした回数であり、EC2やRDSの状態遷移完了を示さない。停止・起動の完了通知が必要な場合は、Targetサービスが発行する状態変更イベントをEventBridgeルールで検知してSNSへ通知する

SQS DLQで失敗理由を確認

  1. TargetErrorCountまたはInvocationDroppedCountが増加したら、Amazon SQSコンソールでScheduleに設定したDLQを開く
  2. メッセージを送受信 ＞ メッセージをポーリングを選択し、受信したメッセージのメッセージ属性を開く
  3. SCHEDULE_ARNまたはTARGET_ARNで対象を特定し、ERROR_CODE、ERROR_MESSAGE、EXHAUSTED_RETRY_CONDITIONを確認
  4. EC2、RDS、WorkSpacesなどTargetサービスのコンソールを開き、対象リソースの状態遷移とイベントを確認
  5. 失敗メトリクスが増えてもDLQが空の場合は、SchedulerからSQSへの送信権限、DLQ ARN、KMSキーポリシーを確認
メッセージ属性切り分けに使用する内容
ERROR_CODE / ERROR_MESSAGETarget APIから返されたエラーコードと原因
SCHEDULE_ARN / TARGET_ARN失敗したScheduleと呼び出し先API
SCHEDULED_TIME / EXECUTION_ID予定実行時刻と実行単位の識別子
RETRY_ATTEMPTSTarget APIを再試行した回数
EXHAUSTED_RETRY_CONDITION最大再試行回数または最大イベント保持時間のどちらを使い切ったか
IS_PAYLOAD_TRUNCATEDDLQへ格納されたInputがサイズ超過で切り詰められたか

SQSコンソールの受信画面はSchedule ARNなどによるサーバー側検索を行わない。メッセージ数が多い場合は、次のCLIで最大10件を受信し、切り分けに必要な属性だけを表示する

CloudShell
aws sqs receive-message \
  --queue-url <SCHEDULER_DLQ_URL> \
  --attribute-names All \
  --message-attribute-names All \
  --max-number-of-messages 10 \
  --query 'Messages[].{MessageId:MessageId,ErrorCode:MessageAttributes.ERROR_CODE.StringValue,ErrorMessage:MessageAttributes.ERROR_MESSAGE.StringValue,ScheduleArn:MessageAttributes.SCHEDULE_ARN.StringValue,TargetArn:MessageAttributes.TARGET_ARN.StringValue,ScheduledTime:MessageAttributes.SCHEDULED_TIME.StringValue,RetryAttempts:MessageAttributes.RETRY_ATTEMPTS.StringValue}' \
  --output table

Universal targetはSchedule作成時にInputの内容をTarget APIの仕様まで検証しない。誤ったリソースIDやJSONでも作成できるため、定期Scheduleの前に同じInputを使用した単発Scheduleで成功を確認する。AWS公式手順：EventBridge Schedulerのトラブルシューティング

CloudTrailで変更履歴をフィルター

  1. CloudTrailコンソールのイベント履歴を開き、Scheduleと同じリージョンと調査対象の時間範囲を選択
  2. 属性イベントソース、値scheduler.amazonaws.comでSchedulerの操作へ絞り込む
  3. 属性をイベント名へ切り替え、CreateSchedule、UpdateSchedule、DeleteScheduleを1つずつ検索
  4. 対象イベントを開き、ユーザー名、イベント時刻、送信元IP、requestParameters、responseElementsを確認
  5. Target APIは属性イベントソースにec2.amazonaws.comなどを指定するか、属性イベント名でStopInstancesやStartInstancesを検索
確認目的属性完全一致で入力する値
Schedulerの管理操作イベントソースscheduler.amazonaws.com
Scheduleの作成イベント名CreateSchedule
Scheduleの変更イベント名UpdateSchedule
Scheduleの削除イベント名DeleteSchedule
EC2停止APIイベント名StopInstances
EC2起動APIイベント名StartInstances
ℹ️ イベント履歴のフィルター制約

CloudTrailのイベント履歴は現在のリージョンにある過去90日間の管理イベントを対象とし、属性フィルターは1回に1つだけ指定できる。イベントソースとイベント名を同時指定できないため、時間範囲を絞ったうえで条件を切り替えて確認する。複数属性や長期データを横断検索する場合はCloudTrail Lakeを使用する

CLIではイベントソースで取得した結果から、Scheduleの作成、変更、削除だけを表示できる

CloudShell
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventSource,AttributeValue=scheduler.amazonaws.com \
  --start-time <START_TIME_ISO8601> \
  --end-time <END_TIME_ISO8601> \
  --query 'Events[?EventName==`CreateSchedule` || EventName==`UpdateSchedule` || EventName==`DeleteSchedule`].[EventTime,EventName,Username,EventId]' \
  --output table

変更時の確認手順

CloudShell
aws scheduler get-schedule \
  --name <SCHEDULE_NAME> \
  --group-name ec2-schedule-group \
  --output json
CloudShell
aws scheduler list-schedules \
  --group-name ec2-schedule-group \
  --output table

作成直後GUIとget-scheduleで時刻、タイムゾーン、Target ARN、Input、実行ロール、Schedule状態を確認
停止前利用者接続、実行中バッチ、バックアップ、メンテナンス、依存先の稼働状況
停止後Targetサービスの状態、InvocationAttemptCount、エラーメトリクス、DLQ、費用影響を確認
起動後リソース稼働、ヘルスチェック、アプリ接続、ジョブ、CloudWatchアラーム、利用者通知を確認
設定変更後変更前後の設定値、今後10回の実行日時、CloudTrailのUpdateSchedule、検証用単発Scheduleの結果を記録
⚠️ 変更時刻と重複実行

実行予定時刻の直前にScheduleを更新すると、変更前の設定で呼び出される可能性がある。変更は実行時刻から離して行い、反映後にGUIとget-scheduleで再確認する。祝日、棚卸し、月次処理などの例外はScheduleの無効化または一時的な時刻変更で管理し、更新APIでは重複実行時の安全性を検証する
