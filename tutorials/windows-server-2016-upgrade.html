Windows Server 2016 インプレースアップグレード

Amazon EC2上のWindows Server 2016を、AWS提供のインストールメディアを使用してWindows Server 2025へインプレースアップグレードする手順を整理する。サポート期限、アップグレードパス、EC2固有の注意点、事後確認までを扱う

1. インプレースアップグレードの概要

インプレースアップグレードは、設定、サーバーの役割、データを保持したまま、既存サーバーのOSを新しいバージョンのWindows Serverへ移行する方式。再構築や移行と比べて作業工数を抑えられる一方、失敗時の切り戻しが難しいため、事前バックアップと事後確認を含めた計画が前提になる

方式内容特徴
インプレースアップグレード 既存OS上で新バージョンをインストールし、設定・役割・データを引き継ぐ 工数が小さい。IPアドレスやインスタンスIDが変わらない。失敗時の切り戻しは事前バックアップ頼み
クリーンインストール + 移行 新規サーバーを構築し、役割・機能・データを移し替える 環境を刷新できる。作業量とダウンタイムが大きい。接続先変更の調整が必要
Automationランブック AWS Systems Managerがインスタンスを複製し、複製側を自動でアップグレードする 元インスタンスを変更せず検証できる。成果物は別インスタンス(別ID・別IP)になる
ℹ️ Automationランブックとの使い分け AWSEC2-CloneInstanceAndUpgradeWindowsは、元インスタンスを複製した側でアップグレードし、検証用の新しいAMIを作成する方式。実行前にランブックのTargetWindowsVersionで対象バージョンを確認し、対象外の場合や既存インスタンスを更新する場合は本ページのインストールメディア方式を使用する

Microsoft公式: Windows Serverアップグレードを計画する / AWS公式: Automationランブックによるアップグレード

2. サポート期限とアップグレードパス

2.1 Windows Server 2016のサポート期限

項目期限
メインストリームサポート終了2022/01/11(終了済み)
延長サポート終了2027/01/12

延長サポート終了後はセキュリティ更新プログラムが提供されないため、それまでに後継バージョンへの移行を完了させる。他バージョンの期限はEOL / ライフサイクル一覧表を参照

2.2 Windows Server 2016からのアップグレードパス

インストールメディアを使用する場合、Windows Server 2016から次のバージョンへ直接アップグレードできる

アップグレード先可否備考
Windows Server 2019可延長サポート終了が2029/01/09と近く、移行先としての価値は低い
Windows Server 2022可従来の「2世代まで」の範囲内。実績記事が多い
Windows Server 2025可Windows Server 2025で非クラスター環境の最大4世代アップグレードがサポートされ、直接移行が可能になった
ℹ️ 最大4世代アップグレード Windows Server 2025以降では、非クラスター環境について一度に最大4世代のインプレースアップグレードがサポートされ、Windows Server 2012 R2以降から2025へ直接移行できる。Windows Server 2022以前をアップグレード先とする場合は従来どおり最大2世代まで

2.3 2022と2025のどちらへ上げるか

観点Windows Server 2022Windows Server 2025
延長サポート終了2031/10/142034/11/14
次回アップグレードまでの猶予短い長い
アプリ・ミドルウェアの対応実績豊富ベンダーの2025対応状況の確認が必要
既定セキュリティ設定の変化小さいSMB署名の既定必須化など影響が大きい。[構築] Windows Server 2025の既定値差分を参照

稼働アプリケーションがWindows Server 2025に対応しているなら、サポート期間の長い2025を選ぶことで次回のアップグレードを1世代分先送りできる。本ページでは2016 → 2025を実施する

3. アップグレードできない・非推奨の構成

ライセンス版(評価版ではない)のインプレースアップグレードには次の制限がある。該当する場合は方式の再検討が必要

構成扱い対応
Active Directory Domain Services(ドメインコントローラー)非推奨技術的には可能だが、Microsoftはクリーンインストールした新規DCの昇格と旧DCの降格を推奨
フェールオーバークラスター不可(方式が異なる)クラスターOSローリングアップグレードを使用。一度に進められるのは1世代のみ
Server Core ⇔ デスクトップエクスペリエンスの切り替え不可同じインストールオプション間でのみアップグレード可能
言語の変更不可OSと同じ言語のインストールメディアを使用する
エディションのダウングレード不可Datacenter → Standardは不可。Standard → Datacenterへの変更は可能
32ビット → 64ビット不可同一アーキテクチャのみ。Windows Server 2008 R2以降は64ビットのみ
VHDブート構成不可クリーンインストールを検討
NICチーミング事前作業が必要アップグレード前に無効化し、完了後に再有効化

Microsoft公式: ドメインコントローラーのアップグレード / Microsoft公式: クラスターOSのローリングアップグレード

4. Amazon EC2固有の注意点

オンプレミスの手順に加えて、EC2では次の点を考慮する

項目内容
バックアップ作業前にAMIを作成する。インプレースアップグレードの確実な切り戻し手段はこのAMIのみ
インストールメディアISOをダウンロードせず、AWSが提供するパブリックスナップショットからEBSボリュームを作成してアタッチする。BYOLの場合は自前のメディアが必要
ネットワークドライバー事前にAWS PVドライバーとENAドライバーを最新化する。ドライバーが古いとアップグレード後にRDP接続できなくなるおそれがある
インスタンスサイズ2 vCPU・4 GiB RAM以上での実施をAWSが推奨。小さいインスタンスは一時的にサイズ変更して実施できる
ルートボリューム空き容量Windowsセットアップは容量不足を警告しない場合がある。旧OSがWindows.oldとして保持される分の空きを確保する
RDP切断セットアップ開始から数分でRDPセッションが切断される。進行状況は「インスタンスのスクリーンショットを取得」で確認する
ステータスチェックアップグレード中は一時的に失敗ステータスになる。監視・自動復旧(オートリカバリ等)を設定している場合は事前に抑止する
所要時間役割とアプリケーションの数に依存し、AWSは40分から数時間かかる場合があると案内
起動エージェントWindows Server 2016 AMIにはEC2Launch v1またはv2が含まれる。アップグレード前後に実際のエージェントと設定を確認し、v1を使用している場合はv2への移行を別作業として計画

AWS公式: EC2 Windowsインスタンスでのインプレースアップグレードの実行

5. 事前検証環境の構築例

5.1 構築例の値

項目値
リージョンap-northeast-1(東京)
AMIWindows_Server-2016-Japanese-Full-Base(最新版)
AMI ID(検証時点)<AMI_ID>
エディションWindows Server 2016 Datacenter(デスクトップエクスペリエンス)
インスタンスタイプt3.medium(2 vCPU / 4 GiB)
ルートボリュームgp3 50 GiB
キーペア<KEY_PAIR_NAME>(RSA)
バックアップAMI ID<BACKUP_AMI_ID>
メディアスナップショットID<MEDIA_SNAPSHOT_ID>
実施日 / 所要時間<UPGRADE_DATE> / <UPGRADE_DURATION>
⚠️ ルートボリューム容量 選択したWindows Server AMIの既定ルートボリューム容量を確認する。アップグレードでは旧OSがWindows.oldとして保持されるため空きを大きく消費する。容量はワークロードに応じて見積もり、本ページの例では起動時に50 GiBへ変更する

5.2 最新AMI IDの取得

AMI IDはリージョンごとに異なり、AWS Windows AMIは月次で更新される。固定値ではなく、SSMパブリックパラメータから実行時点の最新AMI IDを取得し、5.1の表へ記録する

powershell
aws ssm get-parameter `
  --name "/aws/service/ami-windows-latest/Windows_Server-2016-Japanese-Full-Base" `
  --region ap-northeast-1 `
  --query "Parameter.Value" `
  --output text

AWS公式: AMIパブリックパラメータの呼び出し

5.3 Windows Server 2016インスタンスの起動

  1. Amazon EC2コンソールで「インスタンスを起動」を選択
  2. 「その他のAMIを閲覧する」から、5.2で取得したAMI IDを検索して選択
  3. インスタンスタイプにt3.mediumを選択
  4. RSAキーペア<KEY_PAIR_NAME>を指定
  5. 検証用VPC・サブネットと、RDP(TCP/3389)を接続元限定で許可するSecurity Groupを設定
  6. ルートボリュームをgp3 50 GiBへ変更してインスタンスを起動

5.4 RDP接続とアップグレード前の記録

Administratorパスワードの取得とRDP接続の手順は[構築] Windows Server 2025の「1. Windowsインスタンス接続」と同じ。接続後、アップグレード前の状態を記録し、サーバー外(手元の端末など)へ退避する

powershell
Get-ComputerInfo -Property WindowsProductName,WindowsBuildLabEx,WindowsEditionID | Out-File -FilePath .\computerinfo.txt
powershell
systeminfo.exe | Out-File -FilePath .\systeminfo.txt
powershell
ipconfig /all | Out-File -FilePath .\ipconfig.txt
powershell
Get-Service | Where-Object { $_.StartType -eq "Automatic" } | Out-File -FilePath .\services.txt

アップグレード後の比較用として、稼働サービス、ネットワーク設定、OSビルドを控える。winverで現在のバージョン表示も取得する

Microsoft公式: Windows Serverのインプレースアップグレードを実行する

6. アップグレード前の準備

6.1 バックアップAMIの取得

  1. Amazon EC2コンソールで対象インスタンスを選択
  2. 「アクション」から「イメージとテンプレート」、「イメージを作成」を選択
  3. イメージ名に用途と日付がわかる名前を入力。例: ws2016-before-upgrade-<UPGRADE_DATE>
  4. イメージを作成し、AMI IDを5.1の表の<BACKUP_AMI_ID>へ記録
  5. AMIのステータスが「利用可能」になることを確認
⚠️ 再起動の有無 既定ではイメージ作成時にインスタンスが再起動される。「再起動しない」を有効にするとファイルシステムの整合性が保証されないため、検証では既定(再起動あり)で取得する

6.2 ネットワークドライバーの確認と更新

現在のENAドライバーとAWS PVドライバーのバージョンを確認

powershell
Get-CimInstance Win32_PnPSignedDriver |
  Where-Object { $_.DeviceName -like "*Elastic Network Adapter*" -or $_.DeviceName -like "*AWS PV*" } |
  Select-Object DeviceName, DriverVersion

最新版でない場合は、AWS公式手順に従いAWS PVドライバーとENAドライバーを更新する。サーバー上のPowerShellから直接ドライバーをダウンロードする場合は、先にTLS 1.2を有効化する

powershell
[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12

AWS公式: PVドライバーのアップグレード / AWS公式: ENAドライバーのインストール

6.3 SSM Agentと起動エージェントの確認

powershell
Get-Service AmazonSSMAgent
powershell
Get-Service | Where-Object { $_.Name -like "*EC2Launch*" -or $_.Name -like "*Ec2Config*" }
ℹ️ EC2Configの置き換えは2016では不要 AWS公式手順にあるEC2Configのアンインストールは、アップグレード元がWindows Server 2012 / 2012 R2の場合の作業。Windows Server 2016 AMIはEC2Launch v1またはv2を使用するため、実際の起動エージェントを確認し、EC2Configを使用していない場合はこの置き換え作業は不要

6.4 ウイルス対策とファイアウォールの一時無効化

ウイルス対策・スパイウェア対策ソフトとファイアウォールはアップグレードプロセスと競合するおそれがあるため、一時的に無効化する。無効化した項目は9章の事後作業で必ず再有効化するため、変更内容を記録しておく

6.5 空き容量の確認

powershell
Get-Volume -DriveLetter C | Select-Object DriveLetter, SizeRemaining, Size

空き容量が不足する場合は、EBSボリュームの拡張とOS側のパーティション拡張を先に実施する

7. インストールメディアの準備

7.1 パブリックスナップショットの検索

AWSはWindows Serverインストールメディアを言語別のパブリックスナップショットとして提供している。ISOのダウンロードとアップロードは不要

  1. Amazon EC2コンソールで「Elastic Block Store」の「スナップショット」を選択
  2. フィルターを「パブリックスナップショット」へ変更
  3. 検索バーで「所有者のエイリアス」、「=」、「amazon」を指定
  4. 続けて「説明」にWindows 2025 Japanese Installation Mediaを入力して検索
  5. 該当スナップショットのIDを5.1の表の<MEDIA_SNAPSHOT_ID>へ記録
⚠️ メディアの言語一致 インストールメディアはOSの言語設定と一致させる。日本語AMIから構築したインスタンスにはJapanese、英語版にはEnglishのメディアを選択する。言語の異なるメディアではアップグレードできない

7.2 ボリュームの作成

  1. 該当スナップショットを選択し、「アクション」から「スナップショットからボリュームを作成」を選択
  2. アベイラビリティーゾーンを対象インスタンスと同じAZへ変更
  3. 他の設定は既定のままボリュームを作成
⚠️ アベイラビリティーゾーンの一致 EBSボリュームは同じAZのインスタンスにしかアタッチできない。既定値のまま作成するとAZ不一致でアタッチに失敗しやすいため、作成時に必ず対象インスタンスのAZへ合わせる

7.3 アタッチとオンライン化

  1. 作成したボリュームを選択し、「アクション」から「ボリュームのアタッチ」を選択
  2. 対象インスタンスとデバイス名(例: xvdf)を指定してアタッチ
  3. RDP接続に戻り、「ディスクの管理」で該当ディスクを右クリックして「オンライン」を選択
  4. エクスプローラーでドライブ(例: D:)としてメディアの内容が見えることを確認
⚠️ ディスクの初期化はしない 「ディスクの管理」で初期化(フォーマット)を実行するとメディアの内容が消える。操作は「オンライン」への切り替えのみ

8. インプレースアップグレードの実行

8.1 セットアップの起動

管理者としてPowerShellを開き、メディアのドライブへ移動してセットアップを実行。ドライブ文字は7.3で認識された値へ読み替える

powershell
D:
powershell
.\setup.exe /auto upgrade /dynamicupdate disable
ℹ️ /dynamicupdate disable の理由 アップグレード中の更新プログラム適用は失敗の要因になるため、AWS公式手順ではDynamic Updateを無効化して実行する。無効化した分の更新はアップグレード完了後にWindows Updateで適用する

8.2 エディションの選択

  1. セットアップ画面で、現在のエディションとインストールオプションに対応するWindows Server 2025を選択
  2. ライセンス条項を確認して同意
  3. 「ファイル、設定、アプリを保持する」が選択されていることを確認してインストールを開始
⚠️ エディションとインストールオプション 既存OSと同じエディション(本ページの例ではDatacenter)、同じインストールオプション(デスクトップエクスペリエンス)を選択する。Server Core版や下位エディションを選ぶとアップグレードを継続できない

8.3 進行状況の確認

セットアップ開始から数分でRDPセッションが切断され、以降はOSへ接続できない。進行状況はコンソール画面のキャプチャで確認する

  1. Amazon EC2コンソールで対象インスタンスを選択
  2. 「アクション」から「モニタリングとトラブルシューティング」、「インスタンスのスクリーンショットを取得」を選択
  3. 「更新プログラムを構成しています」などの表示と進捗率を確認
  4. スクリーンショットを更新しながら完了まで待機。CPUとディスクのCloudWatchメトリクスでも進行を確認
⚠️ ステータスチェックの一時失敗 アップグレード中はインスタンスステータスチェックが一時的に失敗状態になり、完了すると回復する。ステータスチェック連動のアラームや自動復旧を設定している場合は、誤検知による再起動を防ぐため事前に無効化する

8.4 完了の確認

  1. スクリーンショットにロック画面が表示されたらアップグレード完了と判断
  2. ステータスチェックが2/2で成功していることを確認
  3. RDPで再接続し、サインインできることを確認
  4. 開始から完了までの時間を5.1の表の<UPGRADE_DURATION>へ記録

9. アップグレード後の確認

アップグレード成功はバージョン表示の確認では終わらない。サービス、ネットワーク、AWS管理機能、ライセンスまで確認して作業完了とする

9.1 OSバージョンの確認

powershell
Get-ComputerInfo -Property WindowsProductName,WindowsBuildLabEx,WindowsEditionID

winverでもWindows Server 2025の表示を確認し、5.4で取得した値と比較する

9.2 OS状態の確認

自動起動サービスの停止有無、イベントログのエラー、ネットワーク設定を事前記録と比較

powershell
Get-Service | Where-Object { $_.StartType -eq "Automatic" -and $_.Status -ne "Running" }
powershell
Get-WinEvent -FilterHashtable @{ LogName = "System"; Level = 1,2 ; StartTime = (Get-Date).AddHours(-6) } | Select-Object TimeCreated, Id, ProviderName, Message
powershell
ipconfig /all
  1. 停止している自動起動サービスの有無と理由を確認
  2. Systemログの重大・エラーイベントを確認
  3. IPアドレス、DNS、デフォルトゲートウェイを6章以前の記録と比較して確認
  4. デバイスマネージャーで警告表示のデバイスがないことを確認
  5. 稼働アプリケーションとタスクスケジューラの動作を確認

9.3 AWS管理機能の確認

powershell
Get-Service AmazonSSMAgent
powershell
Get-CimInstance Win32_PnPSignedDriver |
  Where-Object { $_.DeviceName -like "*Elastic Network Adapter*" -or $_.DeviceName -like "*NVMe*" } |
  Select-Object DeviceName, DriverVersion
  1. SSM Agentの稼働と、Systems Manager Fleet Managerでマネージドノードとして表示されることを確認
  2. Nitro世代のインスタンスではENAドライバーとNVMeドライバーの状態を確認
  3. .NET Frameworkの更新を求められた場合は適用して再起動を実行
ℹ️ EC2Launch v2への移行 インプレースアップグレード後も、アップグレード前の起動エージェントと設定を引き継ぐ可能性がある。EC2Launch v1またはv2のいずれを使用しているかを確認し、v1を使用している場合は運用標準と互換性を確認したうえでv2への移行を別作業として計画する

AWS公式: EC2Launch v2エージェント

9.4 ライセンス認証の確認

powershell
cscript //nologo $env:windir\System32\slmgr.vbs /dlv

ライセンス込み(License Included)のAWS提供AMIではWindowsのライセンス認証はAWS側の仕組みで行われる。ライセンスの状態が「ライセンスされています」であることを確認

9.5 Windows Updateの適用

Dynamic Updateを無効化してアップグレードしたため、完了後にWindows Updateで最新の更新プログラムを適用し、再起動まで実施する

9.6 事後作業

  1. 6.4で無効化したウイルス対策ソフトとファイアウォールを再有効化
  2. 8.3で無効化した監視・アラーム・自動復旧を再有効化
  3. インストールメディアのEBSボリュームをデタッチして削除
  4. 動作確認の完了後、不要になった検証用リソース(インスタンス、バックアップAMIと関連スナップショット)を削除してコストを抑止

10. トラブルシューティングとロールバック

10.1 セットアップログの確認

アップグレード後の動作が想定と異なる場合、またはアップグレード自体が失敗した場合は、セットアップログを確認する

確認先内容
C:\Windows\PantherWindowsセットアップのログファイル一式
SetupDiagMicrosoft提供のログ解析ツール。失敗原因の特定に使用
インスタンスのスクリーンショット / システムログOSへ接続できない場合のコンソール状態の確認

数時間経過してもステータスチェックが回復しない場合は、AWSのトラブルシューティング手順に従う

Microsoft公式: SetupDiag / AWS公式: OSアップグレードのトラブルシューティング

10.2 ロールバック

インプレースアップグレードの確実な切り戻し手段は、6.1で取得したバックアップAMIからの復旧のみ。復旧手順を事前に決めてから作業に着手する

  1. 失敗したインスタンスを停止
  2. <BACKUP_AMI_ID>から同じサブネット・Security Groupで新しいインスタンスを起動
  3. 固定IPが必要な場合はElastic IPまたはENIの付け替えを実施
  4. アプリケーションの動作と接続性を確認
  5. 失敗した側のインスタンスは原因調査後に削除
⚠️ 本番適用の判断 復旧後のインスタンスはIDが変わり、EIP・ENI・監視・バックアップ設定の付け替えが必要になる。本番環境では、この切り戻し影響まで含めて検証環境で一度リハーサルしてから適用を判断する
