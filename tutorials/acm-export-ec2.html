ACM証明書をEC2へ自動配置

エクスポート可能なAWS Certificate Managerパブリック証明書をEC2上のApacheへ配置し、AWS Workload Credentials Providerで定期取得、ファイル更新、Apache再読み込みを自動化します。手動エクスポートで証明書形式を理解した後、自動配置へ切り替える

⚠️ ALBで終端できる場合はALBと通常のACM証明書を優先

EC2でTLSを直接終端する要件がなければ、Application Load BalancerでTLS終端へ移行した方が秘密鍵、配布処理、Apache再読み込みを管理せずに済みます。このページは、サーバー内でTLSを終端する明確な要件がある場合の手順

ℹ️ AWS Workload Credentials Providerの動作

プロバイダーは24時間ごと、サービス起動時、システム起動時にACMから証明書をエクスポートし、ローカルファイルと比較します。内容が変わった場合だけ証明書ファイルを書き換え、設定したrefresh_commandを実行する。内容が同じ場合はApacheを再読み込みしない

エクスポート可能なパブリック証明書は有料で、発行時と更新時にドメイン単位の料金が発生します。2026年8月時点の証明書有効期間は198日で、ACMは期限45日前から更新しますが、更新後の証明書をEC2へ配置する処理は利用者側の責任

⚠️ 発行済み証明書のエクスポート設定は後から変更できない

通常の非エクスポート型ACM証明書を発行した後で、エクスポート可能へ変更することはできません。証明書リクエスト時にエクスポートを有効化した新しい証明書が必要

1. エクスポート可能な証明書の発行

  1. ACMコンソールをap-northeast-1で表示
  2. パブリック証明書のリクエストを選択
  3. ドメイン名へserver-tls-lab.zexample.comを入力
  4. 検証方法へDNS検証を選択
  5. キーアルゴリズムをクライアント要件に合わせて選択
  6. 証明書のエクスポートを有効化
  7. 証明書をリクエスト
  8. ACMが提示する検証用CNAMEを公開DNSへ登録
  9. 証明書ステータスが「発行済み」になることを確認
  10. 証明書ARNと有効期限を作業記録へ保存

AWS CLIでリクエストする場合は、Export=ENABLEDを明示する

AWS CLI
aws acm request-certificate \
  --domain-name server-tls-lab.zexample.com \
  --validation-method DNS \
  --key-algorithm RSA_2048 \
  --options Export=ENABLED \
  --region ap-northeast-1

2. 手動エクスポートとApacheへの配置

2.1 エクスポート

この手順は、先に「3. AWS Workload Credentials Provider用IAM」の2つのロールを作成し、EC2へEC2WcpInstanceRoleを関連付けてから実行します。作業用ディレクトリとパスフレーズファイルを作成し、パスフレーズファイルの末尾には改行を入れない

prepare
export ACM_EXPORT_WORK="/tmp/acm-export-work-${USER}"
umask 077
mkdir -p "${ACM_EXPORT_WORK}"

read -rsp 'Export passphrase: ' ACM_EXPORT_PASSPHRASE
printf '\n'
printf '%s' "${ACM_EXPORT_PASSPHRASE}" > "${ACM_EXPORT_WORK}/passphrase.txt"
unset ACM_EXPORT_PASSPHRASE

EC2インスタンスロールを基点にACMExportRoleを引き受け、取得した一時認証情報を現在のシェルだけへ設定する

assume export role
read -r AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN < <(
  aws sts assume-role \
    --role-arn arn:aws:iam::<ACCOUNT_ID>:role/ACMExportRole \
    --role-session-name acm-manual-export \
    --duration-seconds 900 \
    --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]' \
    --output text
)

export AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN

対象証明書をJSON形式でエクスポートする

export certificate
aws acm export-certificate \
  --certificate-arn <CERTIFICATE_ARN> \
  --passphrase "fileb://${ACM_EXPORT_WORK}/passphrase.txt" \
  --region ap-northeast-1 \
  > "${ACM_EXPORT_WORK}/acm-export.json"

unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN

証明書、チェーン、暗号化された秘密鍵をJSONから分離する

split files
sudo dnf install -y jq

jq -r '.Certificate' "${ACM_EXPORT_WORK}/acm-export.json" \
  > "${ACM_EXPORT_WORK}/server.crt"

jq -r '.CertificateChain' "${ACM_EXPORT_WORK}/acm-export.json" \
  > "${ACM_EXPORT_WORK}/chain.pem"

jq -r '.PrivateKey' "${ACM_EXPORT_WORK}/acm-export.json" \
  > "${ACM_EXPORT_WORK}/private-key-encrypted.pem"

Apacheが起動時にパスフレーズ入力を要求しないよう、暗号化された秘密鍵から実行用秘密鍵を作成する

decrypt private key
openssl pkey \
  -in "${ACM_EXPORT_WORK}/private-key-encrypted.pem" \
  -passin "file:${ACM_EXPORT_WORK}/passphrase.txt" \
  -out "${ACM_EXPORT_WORK}/server.key"

2.2 証明書と秘密鍵の検証

verify
openssl x509 \
  -in "${ACM_EXPORT_WORK}/server.crt" \
  -noout -subject -issuer -serial -dates -ext subjectAltName

openssl x509 -in "${ACM_EXPORT_WORK}/server.crt" -pubkey -noout | openssl sha256
openssl pkey -in "${ACM_EXPORT_WORK}/server.key" -pubout | openssl sha256

openssl verify \
  -untrusted "${ACM_EXPORT_WORK}/chain.pem" \
  "${ACM_EXPORT_WORK}/server.crt"

2つのSHA-256値が一致し、証明書のSAN、有効期限、チェーン検証が正常であることを確認する

2.3 Apacheへの配置

install certificate files
sudo install -d -m 700 -o root -g root /etc/httpd/conf/ssl

sudo install -m 600 -o root -g root \
  "${ACM_EXPORT_WORK}/server.crt" \
  /etc/httpd/conf/ssl/server-tls-lab.zexample.com.crt

sudo install -m 600 -o root -g root \
  "${ACM_EXPORT_WORK}/server.key" \
  /etc/httpd/conf/ssl/server-tls-lab.zexample.com.key

sudo install -m 600 -o root -g root \
  "${ACM_EXPORT_WORK}/chain.pem" \
  /etc/httpd/conf/ssl/server-tls-lab.zexample.com-chain.pem

Apacheの443 VirtualHostから配置したファイルを参照する

Apache VirtualHost
<VirtualHost *:443>
    ServerName server-tls-lab.zexample.com
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile /etc/httpd/conf/ssl/server-tls-lab.zexample.com.crt
    SSLCertificateKeyFile /etc/httpd/conf/ssl/server-tls-lab.zexample.com.key
    SSLCertificateChainFile /etc/httpd/conf/ssl/server-tls-lab.zexample.com-chain.pem

    ErrorLog /var/log/httpd/server-tls-lab_error.log
    CustomLog /var/log/httpd/server-tls-lab_access.log combined
</VirtualHost>
Apache checks
sudo apachectl configtest
sudo systemctl reload httpd

openssl s_client \
  -connect server-tls-lab.zexample.com:443 \
  -servername server-tls-lab.zexample.com \
  -showcerts < /dev/null 2>/dev/null |
  openssl x509 -noout -subject -issuer -serial -dates
⚠️ 手動作業用ファイルを残さない

動作確認後は、暗号化解除済み秘密鍵、JSON、パスフレーズを含む作業ディレクトリを組織の鍵管理手順に沿って安全に削除します。削除前に、Apacheが本番配置先のファイルを参照していることを確認する

3. AWS Workload Credentials Provider用IAM

3.1 EC2インスタンスロール

EC2WcpInstanceRoleへ、証明書エクスポートロールだけを引き受ける権限を追加する

EC2 role policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AssumeAcmExportRole",
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::<ACCOUNT_ID>:role/ACMExportRole"
    }
  ]
}

3.2 証明書エクスポートロール

ACMExportRoleの信頼ポリシーで、EC2インスタンスロールだけを許可する

ACMExportRole trust policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustEc2WcpInstanceRole",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<ACCOUNT_ID>:role/EC2WcpInstanceRole"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

ACMExportRoleへ、対象証明書1つだけをエクスポートする権限を追加する

ACMExportRole permissions policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ExportSingleCertificate",
      "Effect": "Allow",
      "Action": "acm:ExportCertificate",
      "Resource": "<CERTIFICATE_ARN>"
    }
  ]
}

EC2へEC2WcpInstanceRoleのインスタンスプロファイルを関連付け、認証情報を確認する

identity check
aws sts get-caller-identity

aws sts assume-role \
  --role-arn arn:aws:iam::<ACCOUNT_ID>:role/ACMExportRole \
  --role-session-name wcp-permission-test \
  --duration-seconds 900 \
  --query 'AssumedRoleUser.Arn' \
  --output text
⚠️ EC2ロールへacm:ExportCertificateを直接付与しない

AWSの構成例と同様に、基点となるEC2ロールと証明書ごとのエクスポートロールを分離します。証明書ARNを限定し、同一アカウント内のすべての証明書をエクスポートできる権限を避ける

4. AWS Workload Credentials Providerの導入

4.1 ソースとバージョンの固定

AWS Workload Credentials Providerはオープンソースです。検証したGitタグを指定して取得し、mainブランチを無条件に本番ビルドへ使用しない

download source
sudo dnf groupinstall -y "Development Tools"
sudo dnf install -y git openssl-devel pkgconfig

git clone \
  --branch <WCP_RELEASE_TAG> \
  --depth 1 \
  https://github.com/aws/aws-workload-credentials-provider.git

cd aws-workload-credentials-provider
git describe --tags --always

AWS公式リポジトリのREADMEとリリースタグを確認し、Rustツールチェーンを導入してバイナリをビルドする

build
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
. "$HOME/.cargo/env"

cargo build --release
file target/release/aws-workload-credentials-provider

4.2 設定ファイルの作成

証明書ARN、引き受けるロール、配置先、Apache再読み込みコマンドをTOMLへ記載する

/tmp/wcp-acm-config.toml
[logging]
log_level = "info"
log_to_file = true

[capabilities.acm]
enabled = true

[[capabilities.acm.certificates]]
certificate_arn = "<CERTIFICATE_ARN>"
role_arn = "arn:aws:iam::<ACCOUNT_ID>:role/ACMExportRole"
certificate_path = "/etc/httpd/conf/ssl/server-tls-lab.zexample.com.crt"
private_key_path = "/etc/httpd/conf/ssl/server-tls-lab.zexample.com.key"
chain_path = "/etc/httpd/conf/ssl/server-tls-lab.zexample.com-chain.pem"
refresh_command = "/bin/systemctl reload httpd"

chain_pathを省略すると、プロバイダーは証明書とチェーンをcertificate_pathへ連結してfullchain形式で保存します。Apache設定とファイル形式を一致させる

4.3 インストール

AWS公式リポジトリに含まれるインストーラーをrootで実行する

install
cd aws_workload_credentials_provider_common/configuration
sudo ./install --config /tmp/wcp-acm-config.toml

インストーラーは専用の低権限ユーザー、systemdサービス、証明書配置先の権限、設定済みのrefresh_commandだけを実行できるsudoersエントリを作成します。/etc/sudoersが/etc/sudoers.dを読み込むことを確認する

sudoers check
sudo visudo -c
sudo grep -R "systemctl reload httpd" \
  /etc/sudoers /etc/sudoers.d 2>/dev/null
⚠️ 長期アクセスキーをEC2へ置かない

EC2ではインスタンスプロファイルから一時認証情報を取得します。アクセスキーをsystemd環境変数、設定ファイル、シェル履歴へ保存しない

6. 設定変更と更新試験

6.1 動的設定再読み込み

証明書、配置先、ロールを変更する場合は、新しいTOMLを指定して動的再読み込みを実行する。設定検証、権限更新、サービス再起動が行われる

configuration reload
sudo aws-workload-credentials-provider \
  acm reload \
  --config /tmp/wcp-acm-config.toml

sudo systemctl status aws-workload-credentials-provider-acm --no-pager
sudo tail -100 /opt/aws/workload-credentials-provider/logs/acm_provider.log

6.2 自動更新経路の検証

ACMの実更新を任意の時刻に強制できないため、初回インストール時の取得、ファイル書き込み、Apache再読み込みを証拠として保存します。さらに隔離した検証環境では、同じFQDNの新しいエクスポート可能証明書を発行し、設定の証明書ARNを変更して動的再読み込みを行うことで、証明書差し替え経路を確認できる

  1. 変更前の証明書serialと有効期限の記録
  2. 同じFQDNを持つ検証用証明書の新規発行
  3. 検証用証明書を対象にしたIAM Resourceの変更
  4. TOML内のcertificate_arn変更
  5. acm reloadの実行
  6. プロバイダーログの更新検知とApache reload成功の確認
  7. ローカルファイルと外部エンドポイントのserial変更確認
  8. 本来の証明書ARNとIAM Resourceへの復元
⚠️ 新しい証明書の発行と更新には料金が発生

エクスポート可能なパブリック証明書は、発行時と更新時に料金が発生します。差し替え試験用の追加発行も課金対象になるため、事前に料金と不要証明書の後片付けを確認する

8. トラブルシューティング

事象確認
エクスポートできない証明書がエクスポート有効で発行されたか、リージョン、ARN、IAM Resourceを確認する
AssumeRoleが拒否されるEC2ロールの権限とACMExportRoleの信頼ポリシーを両方確認する
証明書ファイルが作成されない配置先の絶対パス、親ディレクトリ、WCPログ、SELinux、ファイル権限を確認する
Apache reloadが失敗するrefresh_commandの絶対パス、sudoers、visudo -c、Apache構文を確認する
ACMは新しいがEC2は古い24時間周期、WCPサービス、対象ARN、比較ログ、書き込み失敗を確認する
EC2は新しいが外部は古いApacheの参照パス、reload結果、DNS、複数EC2への配布漏れを確認する
秘密鍵をApacheが読めない所有者、権限、SELinuxコンテキスト、暗号化状態、秘密鍵形式を確認する
証明書と秘密鍵が不一致両方の公開鍵ハッシュを比較し、同じ更新単位のファイルへ戻す

9. ACMEとの使い分け

AWSは、公開証明書を利用者管理サーバーへ自動発行・更新する方式としてACMEを第一候補に案内し、ACMEを利用できない場合の代替としてエクスポート可能なACM証明書とAWS Workload Credentials Providerを案内しています。ACMEでは秘密鍵をクライアント側で生成し、ACMから秘密鍵をエクスポートしない

観点ACM ACMEエクスポート証明書とWCP
秘密鍵ACMEクライアントで生成ACMが保持し、WCPがエクスポート
有効期間45日198日
更新主体CertbotなどのACMEクライアントACMが更新し、WCPが24時間ごとに再配置
主な利点標準プロトコル、サーバー側で発行と配置を完結ACM上で証明書を集中管理
主な注意ACMEエンドポイント、EAB、クライアント運用が必要発行・更新料金、IAM、秘密鍵エクスポートが必要

ACME、料金、有効期間、EventBridgeとSystems Managerを含む方式比較は、AWS Certificate Manager (ACM) と証明書運用を参照する
