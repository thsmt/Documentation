EventBridge Scheduler 自動停止・起動

自動停止・起動を適用できる主なサービス

対象可否は「サービス名」ではなく「そのAPI操作がUniversal targetで利用可能か」「リソースが状態遷移をサポートするか」「実行ロールに権限があるか」で判断する

サービス代表API用途と主な制約
Amazon EC2stopInstances / startInstancesEBSルートボリュームのインスタンスに適用。停止中はパブリックIPv4アドレスが変わる場合がある
Amazon RDS DB instancestopDBInstance / startDBInstance開発・検証DB向け。停止状態は最大7日で、その後は自動起動。読み取りレプリカや構成によって停止不可の場合がある
Amazon Aurora / RDS Multi-AZ DB clusterstopDBCluster / startDBClusterDBインスタンスではなくクラスター操作を使用。対応エンジン・構成を事前確認
Amazon WorkSpaces PersonalstopWorkspaces / startWorkspacesAutoStopまたはManualの停止済みWorkSpaceを開始可能。1リクエストで最大25台を指定
Amazon WorkSpaces PoolsstopWorkspacesPool / startWorkspacesPoolPersonalとは別APIを使用。プールのセッションと利用時間を考慮して停止時刻を設計
Amazon Redshift provisionedpauseCluster / resumeCluster停止ではなく一時停止・再開。再開まで数分以上かかる場合があり、停止不可なクラスター条件がある
Amazon WorkSpaces ApplicationsstopFleet / startFleetAlways-OnまたはOn-Demandフリートで使用。利用者セッション、Auto Scaling、フリート種別を確認
Amazon ECS / Auto ScalingupdateService / updateAutoScalingGroupdesired countや最小・最大容量を変更する方式。復帰値を入力へ固定するため、状態を保持するワークフローを推奨
Lambda / Step Functions / Glueinvoke / startExecution / startJobRun常駐リソースの停止ではなく、定期処理の開始に使用

DocumentDB、Neptune、AppStream 2.0などにも状態変更APIがある。採用前に対象リージョン、リソース状態、API入力、料金、サービス固有の制約を公式ドキュメントで確認する

作業前の確認

対象リソース、依存サービス、停止可能時間、復帰に必要な時間、停止中も発生する料金、実行失敗時の連絡先を記録する。停止対象はタグで管理し、リソースIDをSchedule入力へ直接書く範囲を最小化する

powershell
aws sts get-caller-identity
powershell
aws ec2 describe-instances `
  --instance-ids <EC2_INSTANCE_ID> `
  --query "Reservations[0].Instances[0].{InstanceId:InstanceId,State:State.Name,RootDeviceType:RootDeviceType,DisableApiStop:DisableApiStop,Tags:Tags}" `
  --output json
powershell
aws rds describe-db-instances `
  --db-instance-identifier <RDS_DB_INSTANCE_IDENTIFIER> `
  --query "DBInstances[0].{Identifier:DBInstanceIdentifier,Status:DBInstanceStatus,Engine:Engine,MultiAZ:MultiAZ,ReadReplicas:ReadReplicaDBInstanceIdentifiers,ReadReplicaSource:ReadReplicaSourceDBInstanceIdentifier}" `
  --output json
powershell
aws workspaces describe-workspaces `
  --workspace-ids <WORKSPACE_ID> `
  --query "Workspaces[0].{WorkspaceId:WorkspaceId,State:State,RunningMode:WorkspaceProperties.RunningMode,DirectoryId:DirectoryId,UserName:UserName}" `
  --output json

実行ロールの作成

Scheduler用の実行ロールは、信頼ポリシーでscheduler.amazonaws.comだけが引き受けられるようにする。次の例はEC2の開始・停止だけを特定インスタンスに許可する最小構成であり、RDSやWorkSpacesを追加する場合は別Statementで対象アクションとリソースを限定する

json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "scheduler.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
powershell
aws iam create-role `
  --role-name <SCHEDULER_ROLE_NAME> `
  --assume-role-policy-document file://scheduler-trust-policy.json
json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["ec2:StartInstances", "ec2:StopInstances"],
    "Resource": "arn:aws:ec2:<REGION>:<ACCOUNT_ID>:instance/<EC2_INSTANCE_ID>"
  }]
}
powershell
aws iam put-role-policy `
  --role-name <SCHEDULER_ROLE_NAME> `
  --policy-name AllowScheduledEc2StartStop `
  --policy-document file://scheduler-ec2-policy.json
⚠️ サービスごとの最小権限

RDSにはrds:StartDBInstanceとrds:StopDBInstance、WorkSpacesにはworkspaces:StartWorkspacesとworkspaces:StopWorkspacesを追加する。IAMのサービス認可リファレンスで、各アクションが指定できるリソースARNと依存アクションを確認してから付与する

Schedule作成手順

EC2停止Schedule

Universal targetのInputには、対象APIのリクエストJSONを文字列として指定する。以下では平日20:00 JSTにEC2を停止するTarget定義とScheduleを作成する

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:ec2:stopInstances",
  "Input": "{\"InstanceIds\":[\"<EC2_INSTANCE_ID>\"]}",
  "RetryPolicy": {"MaximumEventAgeInSeconds": 3600, "MaximumRetryAttempts": 3}
}
powershell
aws scheduler create-schedule `
  --name <EC2_STOP_SCHEDULE_NAME> `
  --schedule-expression "cron(0 20 ? * MON-FRI *)" `
  --schedule-expression-timezone "Asia/Tokyo" `
  --flexible-time-window '{"Mode":"OFF"}' `
  --target file://target-ec2-stop.json `
  --state ENABLED

EC2起動Schedule

起動用は停止用と別のTarget定義を使用し、業務開始より前の時刻へ設定する。起動後のアプリケーション初期化時間、EBSボリュームチェック、監視エージェントの起動時間を含めて時刻を決める

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:ec2:startInstances",
  "Input": "{\"InstanceIds\":[\"<EC2_INSTANCE_ID>\"]}",
  "RetryPolicy": {"MaximumEventAgeInSeconds": 3600, "MaximumRetryAttempts": 3}
}
powershell
aws scheduler create-schedule `
  --name <EC2_START_SCHEDULE_NAME> `
  --schedule-expression "cron(0 8 ? * MON-FRI *)" `
  --schedule-expression-timezone "Asia/Tokyo" `
  --flexible-time-window '{"Mode":"OFF"}' `
  --target file://target-ec2-start.json `
  --state ENABLED

RDS DB instance停止・起動

RDSではDBInstanceIdentifierを入力に指定する。停止できない構成ではAPIが失敗するため、事前確認の結果とDLQを必ず確認する。停止状態を7日より長く維持する設計には向かない

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:rds:stopDBInstance",
  "Input": "{\"DBInstanceIdentifier\":\"<RDS_DB_INSTANCE_IDENTIFIER>\"}"
}
json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:rds:startDBInstance",
  "Input": "{\"DBInstanceIdentifier\":\"<RDS_DB_INSTANCE_IDENTIFIER>\"}"
}

Amazon WorkSpaces Personal停止・起動

WorkSpaces Personalは、単一または最大25台のWorkSpace IDをAPI入力に指定する。利用者が接続中の時間帯に停止すると業務影響があるため、通知、猶予時間、例外対象を運用設計に含める

json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:workspaces:stopWorkspaces",
  "Input": "{\"StopWorkspaceRequests\":[{\"WorkspaceId\":\"<WORKSPACE_ID>\"}]}"
}
json
{
  "RoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/<SCHEDULER_ROLE_NAME>",
  "Arn": "arn:aws:scheduler:::aws-sdk:workspaces:startWorkspaces",
  "Input": "{\"StartWorkspaceRequests\":[{\"WorkspaceId\":\"<WORKSPACE_ID>\"}]}"
}

確認・監視・変更管理

Schedule作成後は、設定値、次回実行時刻、実行ロール、Target ARN、入力JSONを確認する。最初の実行は検証リソースで実施し、対象サービスの状態遷移、CloudTrailイベント、CloudWatch LogsまたはDLQ通知を確認してから本番相当の対象へ広げる

powershell
aws scheduler get-schedule `
  --name <SCHEDULE_NAME> `
  --group-name default `
  --output json
powershell
aws scheduler list-schedules `
  --group-name default `
  --output table
確認タイミング確認内容
作成直後時刻、タイムゾーン、Target ARN、Input、実行ロール、Schedule状態
停止前利用者接続、実行中バッチ、バックアップ、メンテナンス、依存先の稼働状況
停止後対象リソースの状態、失敗応答、DLQ、監視アラーム抑止の要否、費用影響
起動後リソース稼働、ヘルスチェック、アプリ接続、ジョブ、監視復帰、利用者通知
⚠️ 例外日と重複実行

祝日、棚卸し、月次処理などの例外は、Scheduleの無効化または一時的な時刻変更で管理する。Schedulerは少なくとも1回の配信を前提とするため、起動・停止以外の更新APIでは重複実行時の安全性を検証する
